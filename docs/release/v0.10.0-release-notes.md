# AI Native ERP v0.10.0

> **发布候选（RC），发布日待定。** 产品代码基线为 main `108684d`（S10 功能全部结案：TINV-05 [#189](https://github.com/lingshf/ai-native-erp/pull/189)、GATE-01 [#188](https://github.com/lingshf/ai-native-erp/pull/188) 合并；PROC-07 [#187](https://github.com/lingshf/ai-native-erp/pull/187)），本 RC 基于 main `58e8422`（Full run 45006555904 绿）。自 v0.9.0（tag 所指提交 `f943b8b`）到 `58e8422` 共 5 个已合并 PR（#186–#190），其中产品与测试提交是 #188、#189。按 D21，tag `v0.10.0` 打在日期 PR 合并后的 squash 提交上，不是 `108684d`；之后 main 只有文档提交，产品代码与 `108684d` 相同。完整变更对比：[v0.9.0...v0.10.0](https://github.com/lingshf/ai-native-erp/compare/v0.9.0...v0.10.0)（tag 创建后可用）。

本地优先、面向小企业的 AI-native ERP，也可用于会计教学（教学说明可关闭）。SQLite、本机单用户、无登录。**非生产演示版。**

版本号取 minor（0.9.0 → 0.10.0）：新增用户可见功能（发票列表筛选）和一个迁移（018，只加一条索引）；请求新增可选参数，响应不变。

## 亮点

- **发票列表可按伙伴、方向、记账日期筛选**：列表上方新增筛选栏，含伙伴代码、方向（全部 / 采购 AP / 销售 AR）、记账日期起止（闭区间）、应用 / 清除；无结果显示“没有符合条件的发票。”。筛选只在页面内有效，不写地址栏，刷新或切换账套后清空（#189；`packages/web/src/TradeInvoices.tsx:1077–1078`、`:1162–1226`、`:1288`）。
- **无功能变化的内部拆分（#188）**：拆出最小常驻闸门；GATE-01 相对其自己的拆分前减少入口 gzip 82 B（Node zlib）。这不是相对 v0.9.0 的版本净变化。
- 证据（来源：PR 正文）：#189 在真实 Chrome 的 `be9f566`（= 最终 head）上跑过 e2e（base、head 各 2/2）和 base / head 截图像素差；#188 在真实 Chrome 的 `a0bc28a`（= 最终 head）上取证。这些是 PR 头提交上的结果，不是合并后的 squash 提交。

## 面向调用方（HTTP API、CLI、迁移）

- **发票列表** `GET /api/v1/trade/invoices`：请求新增可选参数 `party`（伙伴代码）、`side`（`AP` / `AR`）、`from`、`to`（记账日期，闭区间，`from > to` 返回 400）（`packages/core/src/contracts/trade-documents.ts:451–464`）。请求 schema 是 strictObject，未知参数仍 400。**响应不变**：不带新参数时，首页与带游标续页的未解析响应体在 base（`c175a32`）与 head 上逐字节相同（672 B 与 668 B，SHA-256 见 #189 正文 §2；用例 `TINV-05 invoice list compatibility…`，`packages/infra/test/application/trade-documents.test.ts:4593–4642`）。
- **迁移**：最新迁移 017 → **018**，只加索引 `trade_documents_party(company_id, party_id, sequence)`，不改表、不改数据（`packages/infra/migrations/sqlite/018-trade-invoice-filters.sql`；用例：`trade-invoice-filters-migration.test.ts`、`trade-documents.test.ts` “a 017 ledger with posted invoices upgrades to 018…”）。已有账套须先显式 migrate 到 018，见“升级与安装”。
- **未变**：过账与匹配规则、发票预览 / 过账请求与响应、CLI、日志、端口、依赖。`git diff --numstat v0.9.0 58e8422 -- packages/core/src packages/infra/src` 只涉及 trade-documents 的契约、应用、HTTP、存储四个文件和 `migrations.ts`；`package.json` 与 lock 无变化。
- 兼容范围：仅限发票列表请求不带新参数时——响应体与 base 逐字节相同，依据是固定夹具上的首页（672 B）与续页（668 B）；响应字段没有增加。带新参数的请求是新用法。其他接口未做逐字节对比。

## 已知限制

- **旧账迁移（M2）仍未完成**：M2-05（演练）与 M2-06（切换）未开始，另需用户授权。
- **筛选不保留**：刷新、切换账套或离开页面再回来都会清空（任务书决定 5；`TradeInvoices.tsx:1077–1078`）；没有地址栏深链接。
- **伙伴筛选是精确的伙伴代码**，不是名称搜索；格式不对时在控件旁提示并且不发请求（`TradeInvoices.tsx:1118–1121`）。
- 订单列表仍没有按开票状态的筛选 / 排序；发票列表“来源订单”列没有筛选。
- **取消离开确认会截断前进历史**（D275，沿用 v0.9.0）。
- **性能预算**：入口 gzip：#189 相对其 base +382 B（Python gzip-9；文案 +384 B、契约 +10 B），#188 相对其 base −82 B（Node zlib gzip-9）；两者基线与压缩实现不同，不能相加得出版本净值，与 v0.9.0 相比的入口净变化未测量。CSS +44 B（#189）。数字取自 PR 正文，发布前未重测。
- 真实 Chrome 的验证在 PR 头提交上，不在合并后的 squash 提交上（见亮点）。
- 发票筛选在 1 万张发票上的热读 p95 为 12.9–15.5 ms（#189 正文 §3，Windows，AMD EPYC 7763）；只有按伙伴筛选走新索引，按方向、按日期沿用公司索引并过滤（`EXPLAIN` 见 #189 §3）。
- Demo 记录与截图（含销售方向，真实 Chrome 临时账套）：见 `docs/demo/v0.10.0`（另一个 PR，合并后链接生效）。

## 升级与安装

见根 [README](../../README.md) 与[用户文档](../user/README.md)。**新增迁移 018**；v0.9.0 账套先在仓库根目录的 PowerShell 里执行（把示例路径换成你的账套文件）：

```powershell
$db = "D:\erp\my-ledger.sqlite"
npm run storage:admin -- migrate --provider sqlite --file $db
```

`migrate` 按账套已记录的迁移编号，从下一个编号起依次补齐未应用的迁移（`packages/infra/src/storage/migrations.ts:412–430`），所以 v0.9.0 之前的受支持账套同一条命令即可升到 018，不需要先用旧版本迁到 017。前提是账套已记录的迁移编号、校验和与表结构指纹都与仓库一致，否则命令以 `SCHEMA_MISMATCH` 退出且不修改账套；本文没有逐个验证更早版本的账套。这条命令不是旧账导入（M2）。无依赖变化。
