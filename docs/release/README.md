# 发布流程

版本管理（Release Manager）维护本流程。版本与 tag 规则来自协调者的决定 D20（按里程碑划分 Sprint；SemVer，tag 写作 `vX.Y.Z`，修复用 Z 位）与 D21（tag 打在发布 PR 合并后的 squash 提交）。**这两条目前没有收录在[路线图 §6 决定记录](../../design/roadmap.md#6-决定记录)**（该表无 D20/D21），实际落实记录见 [CHANGELOG](../../CHANGELOG.md) 各版本说明和 `docs/release/v*-release-notes.md`（“按 D21，tag … 打在本发布 PR 合并后的 squash 提交上”）。待协调者把 D20/D21 补进 §6 后，这里改为链接到该表。

## 顺序

1. **发布候选（RC）**：开一个发布 PR，只改文档与发布文件（CHANGELOG、`docs/user`、`docs/flows`、`docs/demo`、`docs/release`）。走评审与 CI。
2. **Demo**：按 [Demo 模板](../demo/TEMPLATE.md)写脚本并实跑。
3. **Sprint 评审**、**回顾**：存为 `docs/release/vX.Y.Z-sprint-review.md`、`vX.Y.Z-retrospective.md`。
4. **tag 与 Release**：发布 PR 合并、main 的 Full 为绿之后，经协调者授权，在**该 PR 的 squash 提交**上打 annotated tag `vX.Y.Z`（D21），再发布 GitHub Release（正文取 release notes，去掉“草稿”字样，相对链接改写为 tag 链接）。
5. 不自行合并、打 tag、开 auto-merge。文档与代码不一致时以代码和测试为准，报告差异，不改代码迁就文档。

## 断言需有来源

发布说明、CHANGELOG、用户文档中的**数字性**和**全称性**断言（例如“所有点击区 ≥ 44px”“行为与上一版相同”“约 7 s”“N 个作业”），每条都要有来源，三选一：

- 测试文件与用例名（或脚本与断言）；
- 截图路径；
- 实测命令及其输出摘要（含 commit SHA）。

没有来源的，收窄说法（写明范围与例外）或删掉。来源写在发布 PR 描述或评审记录中，不要求写进说明正文。

### 来源写法示例（抽查 v0.3.0 发布说明，只演示，不改历史文档）

| 断言（v0.3.0 发布说明） | 来源 | 核对结果 |
| --- | --- | --- |
| “自 v0.2.0（`037b3ce`）以来合并 25 个提交” | 命令 `git rev-list --count 037b3ce..c7e5783` 输出 `25` | 一致 |
| “现为 6 个 browser + 6 个 unit 作业” | `.github/workflows/full.yml`：`matrix.shard: [1..6]`，注释“Unit and browser use 6 shards each”，lane 为 unit 与 browser | 一致 |
| “窄屏与粗指针下按钮等控件 ≥ 44 px” | `design/reviews/UI-1.md` 检查项 2：**仅覆盖 390 px 宽**下可见控件 ≥ 44px，表格内禁用的复选框不计（D-6）；明细见该文 §4。**粗指针（pointer: coarse）条件不在此证据内** | 部分有来源：390 px 成立；粗指针未覆盖，应删去或补证据；“等控件”也应写出例外 |

## 发布说明与 CHANGELOG 中的每个数字都要写三项

发布说明和 CHANGELOG 条目里出现的每个数字（体积、耗时、数量、百分比、字节差等），必须在同一处写明：

- **测量对象（artifact）**：量的是什么，例如某个路由的 JS 包、首屏入口文件、某个 CI 作业、某个测试集；不同对象的数字不得混写在一条里。
- **测量方法**：怎么量的，含口径与条件（例如文件名哈希屏蔽后经 gzip-9 压缩、取几次中位数、视口与浏览器），以及对比的两个 SHA。
- **来源 PR**：数字出自哪个 PR（或其评审、CI 记录），写成 `#号`。

缺任一项的数字，补全或删掉。

**提交评审前的核对**：版本管理逐个数字对照其来源 PR 中的数据表，核对一致后才提交评审，并在 PR 正文列出核对结果（数字、所在文件、来源 PR 的表与行、一致或不一致）。有不一致的，先改文档再提交。判定为“视同 ±0”之类的结论，要同时写出所依据的决定编号（如 D454）和原始实测值。

## 范围类断言：写“适用范围 + 例外”

尺寸、数量、覆盖范围这类断言（“全站”“所有页面”“其余控件”“未列出的控件”）最容易被概括句外推。规则：

- 写出**适用范围和例外**，并引用 CSS 文件与行号，或附实测表（页面 × 控件 × 实测值，含视口、浏览器、commit SHA）。
- 不写“全站”“所有”“其余”，除非有覆盖全站的测试或逐页实测表。
- 概括句必须逐条对照来源：来源只证明所列控件，概括句就只能写所列控件。

正确写法示例（行号为 main `28f9de8` 时的位置，写发布说明时按当时的 SHA 重新核对）：

- 44px：（写于 main `28f9de8`；**#126 已删除该全局规则**，此处仅作“范围 + 例外 + 行号”写法示例，不再描述当前代码）`packages/web/src/styles.css:8-11` 的 `button, select { min-height: 44px }` 当时是**未被其他样式覆盖**的 `button` / `select` 的最小高度基线；被覆盖的有分段按钮（`packages/web/src/theme/components.css:364`，`calc(var(--control-h) - 6px)`）。
- 36px：`--control-h` 在桌面为 36px（`packages/web/src/theme/tokens.css:51`），只适用于 #92 / #97 / #98 所列页面的控件；窄屏或粗指针下为 44px（`packages/web/src/theme/shell.css:133`，粗指针未做真机实测）。

## 面向调用方与面向界面的变化分条写

同一个 PR 既改 API / CLI 又改界面时，**分成两条**，各写旧值 → 新值：

- 面向调用方（HTTP API、CLI、日志、端口、迁移编号）：**没变也要明确写“未变”**，并写出依据（测试或差异命令）。
- 面向界面（页面、文案、控件、截图）：只写用户看得到的变化。
- 不要把“界面预填的新值”和“API 的旧值”写在同一条里：读者会以为 API 行为变了（例如订单行号：GUI 自动编号 `L1`、`L2`，API 的行号字段未变）。
- **GUI 变而 API 未变**是最常见的情形，同样要写两条：界面条写新旧表现，调用方条写“API 未变”，依据是未改动 API 的差异命令（如 `git diff 产品基线SHA..当前head -- packages/api`，路径按实际）或通过的契约测试，并写出对比的两个 SHA。不要因为“没有 API 变化”就省略这一条。

## 两种 SHA 要分开写

- **产品基线 SHA**：被描述的产品代码所在的提交（main 上最后一个产品代码提交，或 tag 目标）。CHANGELOG、release notes、Demo 的“源码 SHA”、截图与测试证据都对应它。
- **PR head SHA**：本文档 PR 当前的 head，会随每次推送变化，只用来核对评审与 CI。
- 文档 PR 往往在产品基线之上只加文档提交：两者不同时，两个都写，并说明“产品代码与基线相同”的依据（差异命令）；不要把 head 当成产品基线，也不要把基线当成 head。PR 正文每次推送后更新 head 与 CI 引用。

| 评审意见 | 违反的规则 | 新规则下的自查方法 |
| --- | --- | --- |
| 36px 被写成全站控件高度；实际只有 #92 / #97 / #98 所列页面沿用 36px，分段按钮是 `calc(var(--control-h) - 6px)` | 范围类断言：写了“全站”，没有适用范围与例外 | 搜索草稿里的“全站”“所有”“其余”，每处到 CSS 里搜索 `control-h`、`min-height` 核对，写出页面清单与例外 |

## 运维可见变化给出对照

日志字段、错误类型、端口、CLI 输出、退出码、迁移编号等变化，在 CHANGELOG 中写**旧值 → 新值**，并说明是否影响 HTTP 响应或脚本。示例：`errorType`：领域 / 存储拒绝的 400 由 `ParseError`、404/409 由 `HttpError` → `DomainRejection`（见 CHANGELOG `[0.3.0]`）。

## 检查清单（发布 PR 评审前自查）

- [ ] 每条数字性 / 全称性断言有来源或已收窄。
- [ ] 尺寸、范围类断言写了“适用范围 + 例外”并引用 CSS 行号或实测表；草稿中没有未经全站测试支撑的“全站”“所有”“其余”。
- [ ] 面向调用方（API / CLI）与面向界面的变化分条写；API 未变的明确写“未变”及依据。
- [ ] 运维可见变化有旧值 → 新值。
- [ ] 任务表（`design/tasks/README.md`）状态与 PR 链接与实际一致。
- [ ] Demo 按模板实跑并记录；截图文件名里的语言、主题、宽度、教学开关在截图前已从页面读取并断言；复跑命令含端口空闲检查与监听进程归属检查。
- [ ] PR 描述里的“产品基线 SHA”是证据所依据的产品提交（rebase 后重新核对）；“PR head SHA”与 CI 引用指向当前 head，每次推送后更新。两者不要互相替代。
- [ ] 产品基线 SHA 与 PR head SHA 分开写；GUI 变而 API 未变的，有“API 未变”条目与差异依据；复跑命令的校验与写入在同一个块内。
- [ ] 复跑命令每轮开头清空 `$server`/`$demo`，seed 前自己校验监听归属，收尾只处理本轮对象。
- [ ] **CHANGELOG 只增不删**：已有版本条目不删不改（含标题），只追加；请求评审前用 `git diff origin/main -- CHANGELOG.md` 确认没有被删除或改写的旧行。（S8 回顾行动项 6）
- [ ] **“已验证”写明命令与取证 head**：文档和 PR 正文里每处“已验证 / 已实跑”都写出所用命令和取证时的 head SHA；与最终合并提交不同时，分开写。（S8 回顾行动项 6）
- [ ] **RC 正文固定“证据索引”节**（S10 回顾行动 3）：RC PR 正文含一节“证据索引”，写明：实际核对时间（UTC）；完整 head SHA 与该 head 的 verify 链接；每个合并任务的 PR、合并提交、main Full 链接与取证 gist（含 commit）；PROC-05 固定负例组逐项结果（含从渲染后的 `<pre>` 复制执行的命令与输出）；对照计划中“不进发布说明”的清单（例如以不合并方式结案的任务）逐项写“未出现”。推送新提交后重新核对并更新。
- [ ] **PR 正文顶部固定“当前状态”节，每次推送后重写**（S16 回顾行动 1）：“当前状态”放在正文最前面，写当前 head SHA、CI、已做 / 未做、是否已跑真实时段；每次推送后整节重写。过时的说法不留在原处，移到末尾的“历史”节并标注当时的 head。正文里不得同时存在“尚未运行”和“已运行”。
- [ ] **RC 的 CHANGELOG 对照 first-parent 日志**（S16 回顾行动 5）：RC 前对照 CHANGELOG 运行 `git log --oneline --first-parent <上一个 tag>..main` 中的每个 PR（本仓库 squash 合并，每行一个 PR），要么有 CHANGELOG 条目，要么注明“无用户可见变化”。已随上一版本发布的 PR（发布分支合回 main 带来的）与只改日期的 PR 单列为不需要条目（DEMO-17 的 RC：#269、#272）。DEMO-17 的 RC 写入 #271（新增）与 #270（变更，注明无用户可见变化）两条。核对结果列入 PR 正文。
- [ ] 只改文档，无真实账套数据。
- [ ] 文档里的可复制命令，用替身（临时账套或假进程）完整跑过成功分支和失败分支，两边的输出摘要都写进 PR 正文；只跑成功路径不算。（S5 行动项 10）
  - [ ] **固定负例组**：请求评审前，对文档里每个可执行块逐项跑下面七项，每项的输出摘要写进 PR 正文，只写“已跑”不算；确实不适用的项在 PR 正文写“不适用：理由”（例如“块不读写文件，第 1–3 项不适用”），不能留空。
    - [ ] 1. 目标目录为空，以及从非空目录删光所有文件后脚本正常返回（两种都要测；空快照照常比较，不被当成“未变”，删光必须报“缺失”）。
    - [ ] 2. 目录含隐藏文件（被计入，不漏掉）。
    - [ ] 3. 文件不可读或被独占锁定（必须失败，不能静默跳过）。
    - [ ] 4. 执行中途抛错：`finally` / 后置检查仍执行，原始异常与检查结果都报告；包括“删光文件后再抛错”。
    - [ ] 5. 端口或监听进程归属在两步之间变化：第二步之前独立检查，变化时第二步不执行。
    - [ ] 6. 按 GitHub 渲染结果验证，不能用对原文 grep 代替：用渲染 API（`gh api -X POST markdown -f mode=gfm -F text=@改动文件`（必须是 `-F`；`-f` 会把 `@文件` 当字面字符串，渲染出的只是一行路径），或 PR 预览）取渲染后的 HTML，确认每个应复制的命令是独立的代码块（`<pre>`），章节正常分段，没有字面转义（`\n`）、拼行、不可见字符；再从渲染结果复制到新终端执行一次。对原文的 `Select-String -Pattern '\\n'` 只是辅助定位，不算本项通过。
    - [ ] 7. 非终止错误（S10 回顾行动 2）：用 PS 5.1 下可复现的真正非终止错误——`Copy-Item` 的源与目标是同一个文件（产生非终止的 `CopyError`）。**不带 `-ErrorAction Stop`**：stderr 报错但块继续执行，`ok` 被设为真（这是要避免的缺陷，两组对照都要留输出）。**带 `-ErrorAction Stop` 的修正版**：进入 `catch`，块以非零退出码结束，`ok`（或等价的成功标记）不为真，源文件（如源截图）仍在、没有被删除。非零退出只约束修正版。PR 正文给出两组的退出码、成功标记的值和源文件仍在的证据；块内每个 cmdlet 都带 `-ErrorAction Stop`。独占锁、同名目录不是可靠的失败场景，不用。
    - 替身场景的写法见 [Demo 模板](../demo/TEMPLATE.md) 的“替身验证”。（S7 回顾行动项 5）
- [ ] 更正历史说法时，先引用原文的适用范围（原句、所在文件与版本），更正只覆盖该范围，不扩大到原文没有说的控件、页面或版本。（S5 行动项 10）
- [ ] **全文核对数字与状态**：请求评审前，对 PR 正文和文档中的每个数字（张数、个数、耗时）、状态（任务表、CI、合并）、PR 号和 SHA 做全文核对，以核对当时 `gh` 的输出为准（例如 `gh pr view 编号 --json state,mergeCommit,headRefOid`，编号换成实际值），并在 PR 正文写明核对时间；之后推送了新提交，就重新核对。（v0.6.0 回顾行动项 3）
- [ ] **“没做的事 / 已知限制”在初稿就写出**：初稿即列出未做、未验证、未演示的项（对照图、未实跑的脚本、未覆盖的分支、已知限制），不等评审指出再补；与已做的项分开写。（v0.6.0 回顾行动项 4）
- [ ] Demo 脚本在申请时段前已写好，并用替身验证过成功和失败分支；含删除 / 复制的替身隔离了 `TEMP`、记录了真实产物前后哈希。（v0.6.0 回顾行动项 1、2，见 [Demo 模板](../demo/TEMPLATE.md)）
- [ ] **行为描述有出处**：发布说明与 Demo README 的“用户可见变化 / 兼容性”每一条行为描述，都附 `file:line` 或用例名；写不出出处的删掉或改成“未验证”。（S9 回顾行动项 6）
- [ ] **范围词逐项枚举**：“全部”“各”“无”“不存在”“硬阻断”等范围词，逐项列出所覆盖的页面或情形，并逐项对照代码；有例外的单列。示例：#182 合并时，“待重试”按页面写的硬拦截只有结算、调整、期间准入三处，发票页的“待重试”不是硬拦截（询问确认后可离开）。（S9 回顾行动项 6）

- [ ] **tag 目标按产品代码核对**（D335 / D398）：日期 PR 写明 tag 目标时，附 `git diff --stat <产品基线> <目标> -- packages` 的输出；为空才可以打在 Demo / 日期 PR 的 squash 提交上，否则选“基线之后、新产品提交之前”的最后一个提交（v0.11.0 的 `024b7fa`），并写明哪些提交因此不在 tag 内。统计固定比较两个具体 SHA，不用会变动的 `origin/main`。（v0.11.0 的 D398）
- [ ] **正文与运行记录一致**（S11 回顾行动 6）：RC / Demo 每次请求评审前，对照 `run-through.md` 检查正文中“未运行 / 待 / TODO / 尚未做”等字样与每次运行的结论，PR 正文中的“已通过 / 已实跑”状态、日志文件名、SHA、行数、哈希、退出码逐条与已提交的日志核对；之后补做的运行，在同一次推送里更新正文和 `run-through.md`。新写的步骤块按 S10 行动 2 逐个 cmdlet 加 `-ErrorAction Stop`。正文改动用 `gh pr edit --body-file`，并写明核对时间。

- [ ] **RC 的体积与耗时数字取自来源 PR 的表**（S15 回顾行动 6）：RC 里每个体积、耗时数字，逐个摘自来源 PR 正文或评论中的表行，原样引用，不改写、不换算、不把不同测量相加；同一处写明测量对象、方法与来源（链接到评论或文件行）。核对结果列入 PR 正文。

## 日期 PR 清单（tag 之前的最后一个发布 PR）

日期 PR 单独开，只改文档（v0.6.0 回顾行动项 5；历史版本的发布物不回补）。清单分两段：**送审前**逐项勾选后再送评审；**合并后**的两项在 PR 合并之后才能完成，不是送审条件。

送审前：

- [ ] CHANGELOG 与 release notes 都填入发布日期，两处一致。
- [ ] **compare 链接给两条**（D483）：发布分支分叉时三点链接 `A...B` 从合并基算起，会重现已发布的文件；所以同时给“完整版本差异”（两点 `A..B`，tag 到 tag 的直接差异，附 `git diff --shortstat A B` 的文件数）和“合并基对比”（三点 `A...B`，写明合并基 SHA 与文件数）。CHANGELOG、release notes、Release 正文三处一致，不把三点链接称为“完整变更对比”。
- [ ] compare 链接已填入（上一版本 tag 到本版本 tag，即 `vX.Y.(Z-1)...vX.Y.Z` 或实际上一版本），`[Unreleased]` 改为 `本版本...HEAD`；tag 创建前 compare 链接不可达，在 PR 中写明，tag 后再核对。
- [ ] 去掉“草稿”等草稿标记（CHANGELOG 与 release notes 两处），并写明产品基线 SHA 与 tag 目标的关系（之后只有文档提交时，写出依据）。
- [ ] 链接到本版本的 Demo 记录（Demo PR 或 `docs/demo/vX.Y.Z/` 的 `run-through.md`），链接能打开。

合并后（由协调者合并；未获授权不打 tag、不发 Release）：

- [ ] 该 squash 提交上 main 的 Full 全绿。
- [ ] 全绿后，按协调者授权在该提交上打 annotated tag、发 Release（见上“顺序”第 4 步）；发布后核对 compare 链接与 Release 正文中的链接能打开。
