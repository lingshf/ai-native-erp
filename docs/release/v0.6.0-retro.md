## 议题 1：Demo 的两类问题（运行记录与脚本安全）

两类问题性质不同，分开写。

**1a. 前两轮主账套运行没有执行 seed**
- **观察**：[run-through](../demo/v0.6.0/run-through.md) 记录：主账套前两次运行没有执行 seed，缺少 `PARTY`，预览返回 400；第三次补上 seed 后成功。三次都已记录，截图取自成功的一次。
- **根因（推断）**：运行前没有对照“账套就绪”清单（含 seed），只检查了端口与进程。
- **改进动作**：Demo 开跑前把 seed 与“预览所需主数据存在”写成脚本里的显式步骤，缺则停止（负责人：版本管理；落到 Demo 模板）。

**1b. 事后整理脚本的安全与验证**
- **观察**：Demo 跑完后，README 复跑命令和两个 PS1 经过多轮评审修订，#151 为此打回 4 轮，各轮的问题不同（[评审时间线](https://github.com/lingshf/ai-native-erp/pull/151)）：
  1. 命令不可直接复制；
  2. capture 非零退出后仍可能复制旧产物；缺少 seed 之后、capture 之前的监听 PID 归属复核（这是后续脚本的另一项安全修订，与 1a 无关）；
  3. 缺少对修订后脚本的运行验证；
  4. 替身未隔离输出、不做断言。
- **观察**：首次替身运行没有隔离 TEMP，删除了真实的 `$env:TEMP\demo-s6-shots`。仓库中已提交的截图不受影响（与 5675c9e 一致），已在 #151 披露。
- **根因（推断）**：脚本是运行之后才整理成可复制形式，没有在运行前按 `docs/demo/TEMPLATE.md` 逐条对照；替身一开始就把会删除目录的操作指向了真实路径。
- **改进动作**：
  - Demo 开跑前先写好脚本，通过替身验证，再申请时段，真实运行用评审过的脚本（负责人：版本管理；落到 Demo 模板）。
  - 含删除/复制的替身必须重定向 TEMP、校验真实产物哈希，并对每个场景断言结果（已在 `stub-check.ps1` 实现；负责人：版本管理）。
  - 脚本中任何写文件的步骤，与其前置检查（端口归属、退出码）放在同一代码块里。

## 议题 2：评审打回的两类原因：报告准确性与披露完整性

- **发生了什么**：#149 打回 2 轮，#152 打回 1 轮；#151 的 4 轮属于议题 1b，不计入本节。
- **报告准确性（#149）**：预览失败的表现误写、锚点错误、已知限制缺 D199、PR 正文里的任务表状态过时、截图张数在 #151 曾写成 18（实为 16）。
- **披露完整性（#152）**：漏写“没有拍摄 UI-12 修复前的迁移页对照图”，以及“只有修订后的脚本没有真实复跑，16 张截图都来自真实 Demo”。这是**漏写**，不是列出了未做的内容。
- **根因（推断）**：数字和状态在多处（CHANGELOG、发布说明、PR 正文、README）各自手写，改一处时漏改另一处；任务表状态是抄来的，而当时的任务表过时；披露只写了已做的、没有按“未做清单”逐项写。
- **改进动作**：
  - 提交前对数字（张数、PR 号、SHA）和状态做全文核对，以 `gh` 当前输出为准（负责人：版本管理）。
  - 引用任务表前先与已合并 PR 对照，有差异先报告设计角色（本 Sprint 已按此处理，#150）。
  - 初稿就列“未做 / 未验证清单”，对比图、复跑、未演示分支逐项写入（负责人：版本管理）。
