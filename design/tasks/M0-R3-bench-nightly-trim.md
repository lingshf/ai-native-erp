# M0-R3 每晚 Bench 精简

- 里程碑：M0 评审后续　依赖：M0-R　建议分支：`bench-nightly-trim`
- **阻塞 M1：否**（建议尽早做）

## 背景

`.github/workflows/bench.yml` 写死了基线 `5b23d8c`，每次运行都要额外检出旧代码、安装依赖，先跑基线再跑候选，还扫描 R=2/3/4。手动运行耗时 17–22 分钟（最长 1316s = 21m56s），其中一部分超过“每晚 Full + Bench ≤ 20 分钟”的预算；定时运行还没有实测。如果每晚都这样运行，一个月约 600 分钟。

同时，判定逻辑（`packages/infra/bench/reports.ts:107,131-141,596-610`）在没有配对基线时把候选判为 MISS，并且写死了 `OLD_MAIN`：传入其他基线 SHA 也会因为不匹配而失败。所以只改 workflow 传参不够，判定逻辑也要改。

## 范围

- 每晚（schedule）和手动时 `baseline` 为空：只跑当前 main 的候选，默认读池大小 R，不扫描。
  - 相对回退判定为 **N/A**（在 summary 中明确写出 N/A，不算通过也不算失败）。
  - **保留 M0-12/M0-13/M0-13a 的全部候选门禁**，阈值不变：热读 p95 ≤ 1s、≤100 行预览/确认 p95 ≤ 2s、主线程事件循环单次阻塞最长 ≤ 100ms 且 p99 ≤ 50ms；场景门禁包括读池饱和时的轻读（含排队时间）及专用槽位被轻读用上的证明、3 个并发请求、未调整报表与六项对账、靠后页耗时及靠后页/首页耗时比。
- 手动（workflow_dispatch）新增输入：
  - `baseline`（commit SHA，默认空）。非空时，在同一 runner 上先跑基线再跑候选，按 M0-13a 现行规则判定相对回退（p50 ≤ 10%；p95/p99 只看绝对预算）。基线结果中记录的 SHA 必须和输入一致，不一致判为失败。
  - `sweep`（布尔，默认否）：是否扫描 R=2/3/4。
- 删除写死的 `5b23d8c` 和 `OLD_MAIN`，基线 SHA 只来自输入。
- 只有一套阈值和一套回退规则，不新增第二套。

## 验收标准

- 每晚（或空 baseline 的手动运行）墙钟 ≤ 10 分钟，给出一次实测 run 链接；summary 中相对回退为 N/A，上面列出的全部候选门禁都有结果并通过。
- 手动带 `baseline` 的运行产出与现在相同的对比表，给出一次实测链接。
- 测试覆盖判定逻辑：空基线 → 回退 N/A、候选门禁照常判定（任一门禁失败则整体失败）；基线 SHA 不匹配 → 失败；匹配 → 按 p50 规则判定。
- CI 绿。

## 性能考虑

只改 CI 编排和判定逻辑，不改基准的数据量和预算。
