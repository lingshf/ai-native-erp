### 现状（main `002c237`）

- `ci.yml` 只有一个 `verify` job（`ubuntu-latest`，`timeout-minutes: 10`，`ci.yml:10–12`），步骤依次为：检查 registry → `npm ci` → Chromium 冒烟 → Biome（`:46–47`）→ Typecheck（`npm run typecheck`，`:48–49`）→ Import boundaries（`:50–51`）→ Shard weight guard → Select tests → Affected tests → Web build → Test timing summary。
- `npm run typecheck` 用根 `tsconfig.json`，不收录 `packages/infra/test/support/**` 与 `test/http/*.slow.test.ts`（[S14 FIX-01 根因 1](S14.md#ci-的-typecheck-为什么没有拦住)）。这两类文件只由 `scripts/slot/tsconfig.preflight.json` 收录，只在时段 runner 里检查（`scripts/slot/README.md` 第 5 行：“不进 Vitest、不进 CI”）。
- `preflight.mjs --root .` 用仓库自己的 `node_modules` 下的 tsc 与 `@babel/parser`，退出码 0 无新发现、4 输入或配置错误、6 有新发现（`scripts/slot/README.md`“开跑前静态检查”一节）。
- 基线键只含错误码与消息，不含文件路径（`preflight/tsc.mjs:48`；TDZ 的显示路径统一为 `/`，`preflight.mjs:96`），所以 Linux 与 Windows 的键一致（推断，C2 在 Linux 上实测确认）。
- **可行性试算**（S12 回顾行动 5、S13 回顾行动 4；本机 Windows，`002c237`，单次）：`node scripts/slot/preflight.mjs --root .` 用时 3.0 s，输出 `tdz files=31 findings=0`、`preflight result exit=0 new-keys=0 reduced-keys=0`；同机 `npm run typecheck` 用时 6.1 s。verify 现有 10 分钟上限内有余量。

### 范围与决定

1. 在 `Typecheck` 步之后加一步，名称如 `Slot preflight (tsc + TDZ, baseline)`，命令 `node scripts/slot/preflight.mjs --root .`。tsc 与 TDZ 两部分都跑：TDZ 基线为 0，同样能拦住时段前才暴露的问题。不加 `--files`。
2. 不加 `if:` 条件，不设 `continue-on-error`：退出码非 0 即让 verify 失败（4 与 6 都失败）。
3. 不改预检语义与基线。基线只减不增（D407 / D408）：PR 若让某个键的计数下降，预检输出 `reduced-keys>0` 但退出码仍为 0；是否顺手下调基线不在本任务范围。
4. `full.yml` 不加：Full 由 push 到 main 触发，PR 层已拦住；时段 runner 仍保留第一步预检（D400），不因 CI 已跑而删除。

- Sprint：S15　依赖：无　建议分支：`tinv-09-credit-reduces-invoiced`
- 冲突域（逐个列文件）：
  - storage：`packages/infra/src/storage/trade-documents.ts`（已开票谓词、状态重算、贷项过账与取消时刷新）；
  - migrations(020)+migrations.ts：新增 `packages/infra/migrations/sqlite/020-<名称>.sql`；`packages/infra/src/storage/migrations.ts`（manifest 数组、`inspectSchema` 的对象检查不变、020 的回填挂钩）；

  - web-ui:trade-orders：只改 `packages/web/src/ui/trade-order-labels.ts` 的 `tord.teaching` 中英各一句；
  - 取证所需观测点 / 新增测试文件：无；
  - **不涉及**：`packages/core/src/application/trade-adjustments.ts` 的贷项金额与数量上限规则；`trade-documents.ts`（core）的匹配容差；契约 schema；页面组件与 CSS；tests:trade-e2e；`docs/user`（由版本管理在 DEMO-15 RC 中改）。
- 类型：功能（贸易单据）
- 优先级：P1（S15 唯一的用户可见功能；S7 起的候选）

### 现状（main `002c237`）

- **唯一的已开票谓词**（TINV-03）：`invoicedOrderLines`（`packages/infra/src/storage/trade-documents.ts:174–178`）只统计“引用订单、所属发票未取消”的发票行，不看贷项。三处使用：
  - `tradeOrderInvoiced`：过账匹配的 `previouslyInvoiced`（`packages/core/src/application/trade-documents.ts:915–930`）与订单详情 `orderInvoicing`（`:1275`）；
  - `tradeOrderPageInvoicedSql` / `tradeOrderStatuses`（`infra …/trade-documents.ts:185–219`）→ `refreshTradeOrderInvoicing`（`:229–245`），写入已保存的 `trade_order_invoicing.status`（迁移 019）。
- **状态刷新时点**：发票过账（`:830`）、发票取消或恢复（`:470–480`）、迁移 019 回填（`migrations.ts:422–439`、`:455–456`）。`:470` 的注释写明“credits have no trade_documents row”，所以贷项过账与取消今天都不刷新状态。
- **贷项数据**：`trade_credit_lines`（迁移 012，`012-trade-adjustments.sql:134–147`）按 `(company_id, credit_id, source_line_id)` 记录贷项数量 `quantity`（十进制文本，没有 micros 列），`source_line_id` 指向原发票行；索引 `trade_credit_lines_source(company_id, invoice_id, source_line_id, credit_id)`。这张表**不可更新、不可删除**（触发器 `:154–155`），所以不能加列回填。贷项取消通过它的未结项 `open_items.status='cancelled'` 表示（`trade-documents.ts:397` 的查询即按此过滤）。
- **数量上限**：同一发票行累计贷项数量不超过该行数量（`core …/trade-adjustments.ts:301–305`，超出报 `quantity`），所以每个发票行的“发票数量 − 贷项数量”不小于 0。
- **现有口径的出处**：TINV-01 决定 2“贷项不冲减（与现行匹配一致）”（`TINV-01-invoice-from-order.md:31`），TINV-03 的“不在范围”（`TINV-03-…md:59`），用户文档 `docs/user/trade.md:48`“贷项、收付款和冲销不改变开票状态”。

### 设计决定（产品负责人）

1. **口径**：订单行的已开票数量 = Σ（未取消发票上引用该订单行的发票行数量）− Σ（这些发票行上未取消贷项的数量）。取消的发票、取消的贷项都不计。这是新的**唯一**谓词，`tradeOrderInvoiced`（匹配与订单详情）与状态重算共用，TINV-01 决定 2 的“单一来源”原则不变，只是口径变了。
2. **被冲回的数量可以再开票**：订单详情的“未开票数量”增加，“开票”按钮带入的草稿按新的未开票数量；过账匹配的 `previouslyInvoiced` 用同一口径，所以再开票不会被判超量。
3. **开票状态**（`none` / `partial` / `full`，判定函数 `tradeOrderInvoicingStatus` 不变）按新的已开票数量计算：全部冲回的订单回到“未开票”，部分冲回的回到“部分开票”。
4. **取消贷项**：已开票数量恢复。若此前已对冲回的数量再开票，取消贷项会让已开票数量超过订单数量；本任务**不拒绝**这种取消，状态按现行规则为“已开完”。与现行“超量开票需匹配例外、但不禁止”一致；取消贷项本身已有的依赖规则（例如已退款须先撤销，`trade-documents.test.ts:1298` 一例）不变。
5. **刷新时点**：在现有两个时点之外，增加贷项过账（`insertTradeAction` 的 `credit` 分支）与贷项取消 / 恢复（未结项状态进出 `cancelled`，该未结项是贷项时），在**同一事务**内刷新受影响订单的状态。受影响订单 = 贷项所针对发票行的 `order_id`。
6. **迁移 020 只重算，不改 schema**：
   - 不给 `trade_credit_lines` 加列（表不可更新）；贷项数量按现有十进制文本，用与发票行相同的 `quantityMicros` 在 JS 中换算为 micros，保证精确。
   - 020 的 SQL 不建、不删、不改任何对象；020 之后的 schema 指纹与 019 相同，`inspectSchema` 的对象清单不变。SQL 文件内容由开发定（例如只有说明注释）；若运行器不接受只有注释的脚本，用一条不改对象的语句，并在 PR 正文写明。
