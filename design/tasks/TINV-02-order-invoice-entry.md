## 现状（main `1bb9dbb`）

- 订单页查看已保存订单时，明细表（`packages/web/src/TradeOrders.tsx:1157` 起）只列订单行与金额，看不出每行已开多少发票、还剩多少；也没有去开票的入口。
- TINV-01 合并后，订单明细每行有 `invoicedQuantity`，发票页可通过 `#/trade-invoices?company=<公司>&fromOrder=<订单号>` 带入草稿。

## 设计决定（产品负责人）

1. **明细表加两列**：“已开票数量”（`invoicedQuantity`）与“未开票数量”（`quantity − invoicedQuantity`，按 `decimal` 精确相减，不经浮点）；未开票为 0 的行在该列显示“已开完”徽标（复用现有徽标组件，不新增颜色）。390 宽度下沿用该表现有的横向滚动 / 换行方式，不另设布局。
2. **“开票”入口**：在已保存订单的详情操作区放一个链接式按钮“开票”，目标为 TINV-01 的入口地址（带当前公司与订单号），用 `Link`，不用 `window.location`。全部行都已开完时禁用，并在旁边说明原因（不是只靠 `title`）。键盘可达，顺序在详情现有操作之后。
3. **不改列表**：订单列表不加开票状态列，不加按开票状态筛选（需要按页聚合，另议）。
4. **筛选重置用例**（S7 遗留 8）：补一条 web 用例：在订单列表设置伙伴 / 方向 / 日期筛选后离开订单页，再返回，筛选控件为空，列表请求不带 `party`、`side`、`from`、`to`。只补用例；若用例失败，说明 TORD-05 的行为与其任务书不符，停下报告设计角色，不在本任务里改筛选逻辑。

## 开工与评审门禁

- TINV-01 开工后，本任务可以按上面写定的契约字段名和入口地址并行开发（web 测试用 mock fetch），只改本任务冲突域内的文件。
- **TINV-01 合并、且覆盖其合并提交的 main Full 变绿之前，本任务不得请求评审**，也不得改动 `scripts/test-shard-weights.json`。门禁满足后 rebase 到该 main，再登记权重（如有新增测试文件）、跑端到端用例、在独占时段取证，然后请求评审。
- 若 TINV-01 评审中契约字段名或入口地址有变，以合并后的 main 为准调整本任务。

## 范围

1. 订单详情明细表两列与“已开完”徽标（决定 1）；中英文 labels。
2. “开票”入口与禁用说明（决定 2）。
3. web 用例：两列取值（含部分开票、全部开完）、入口链接地址、全部开完时禁用与说明、筛选重置（决定 4）。
4. 端到端（真实 Chrome，`tests:trade-e2e`）：在现有贸易 GUI 场景中追加一条路径：新建订单 → 订单页“开票” → 发票页带入 → 填外部发票号 → 预览 → 过账 → 回订单页，已开票 / 未开票数量更新；再开一次至全部开完，入口变为禁用。优先追加到现有场景与用例文件；只有现有文件放不下时才新增文件，新增时登记权重。
