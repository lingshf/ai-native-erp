## TINV-07：发票详情深链接与筛选写入地址栏

### 现状（main `f5defcc`）

- 页面用 `useSearchParams`（`packages/web/src/TradeInvoices.tsx:303`），只读 `company`（:304）；`fromOrder` 一次性读取后用 `setParams(..., { replace: true })` 删除（:308–332）。
- 筛选（TINV-05）只在内存里、按公司保存，刷新或切换公司即清空；`apply`（:1116–1125）修剪 `party`、按 `companyCodeSchema` 校验、`from > to` 报 `range`。
- 详情（TINV-06）为 `useState`（:1133），设计决定 2 明确“不改地址栏”。本任务推翻该决定，属于用户可见变化。
- 离开确认 `useInvoiceLeaveGuard`（:206 起）：渲染后 `useLayoutEffect` 调用 `history.current?.settle()`（:213），使页面改写自身地址时更新 `here`；历史闸门 `guardHistory`（`packages/web/src/leave-guard-history.ts:28–41`）按**完整 href** 比较，取消时 `pushState(here)`（D275），从不调用 `history.go`；`installGate` 在 HashRouter 之前安装（`leave-guard-gate.ts:18`，D280）。

### 设计决定（D370 已决，开发方案已批准）

开发方案见 TINV-07 开发 session 的 `plan.md`（第 1–7 节）；以下为产品口径，冲突时以本节为准。

1. **A：只用 `replace`**。打开 / 关闭详情、应用 / 清除筛选、切换账套，全部 `setParams(next, { replace: true })`（底层 `history.replaceState`），`history.length` 不变。不调用 `pushState`、`history.go`，不新增 `popstate` / `hashchange` / `beforeunload` 监听，不改 `leave-guard-history.ts`、`leave-guard-gate.ts` 与 `App.tsx` 安装顺序。`replaceState` 不触发 `popstate` / `hashchange`，因此草稿 dirty 时这些操作都**不弹确认**；渲染后的 `settle()`（:213）把闸门的 `here` 刷成最新地址，取消“后退”时 `pushState(here)` 恢复的是含筛选 / `invoice` 的地址。“后退”语义不变：直接离开发票页（dirty 时问一次），不会只关对话框（TINV-06 验收 9 不变）。
2. **只在用户操作时写地址**。挂载 / 刷新时不做规范化改写（不删非法参数、不补 `company`），唯一例外是现有 `fromOrder` 的读取后删除（:308–332，不改）。写入辅助函数以调用时的 `window.location` 合并参数，不用渲染闭包中的旧 `params`。
3. **B：每次写入都带 `company`**，切换账套时写入新代码，并同时删除 `party/side/from/to/invoice`（草稿按账套分存，现状不变）。
4. **地址是唯一事实源**：已应用的筛选 = 解析地址；打开的详情 = 地址中的 `invoice`。刷新后筛选与详情恢复（改变 TINV-05“刷新清空筛选”的行为，发布说明须写明）。手改地址栏经现有闸门（dirty 时问一次），接受后按新地址重新解析；筛选栏输入框在已应用值变化时重置为已应用值。
5. **`cursor`、`limit` 不写地址**：深链接总从首页开始。
6. **未知参数原样保留**，重复参数取第一个（`URLSearchParams.get`），写入时 `set` 覆盖为单个。
7. **C：筛选参数整组判定**：`party/side/from/to` 中任一非法时整组忽略——列表按无筛选加载（不把非法值发给接口，不产生 400），筛选栏上方显示一条 warning 提示与“清除”按钮。
8. **D：`invoice` 格式非法时前端直接判 notFound，不发请求**。格式规则与服务端一致（`/^[0-9a-f-]{36}$/`，`packages/core/src/application/trade-documents.ts` 中详情查询的同一规则）。
9. **E：授权修改 4 处现有“地址不变”断言**（D370），只改成新行为，**不删除、不跳过**：
   - `packages/web/test/trade-invoices.test.tsx:1070–1114`（TINV-05“应用筛选不改 href、不调用 pushState/replaceState”）→ 只调用 `replaceState`、不调用 `pushState`、`history.length` 不变、hash 含已应用筛选；
   - `packages/web/test/trade-invoice-detail.test.tsx:513–539`（打开前后 hash 相等）→ 打开时含 `invoice=`，关闭后回到打开前；`history.length`、`confirm` 断言保留；
   - `packages/infra/test/support/trade-gui-scenario.ts` `invoiceFilters()` 的 `unchanged()` → hash 等于期望的筛选地址；`dialog` 计数 0 保留；
   - 同文件 TINV-06 步骤的 `snapshot()` → 打开前 / 关闭后 hash 相等（若导航时未带 `company`，改为比较除 `company` 外相等）。
   其他现有断言不在授权范围内；如需改动，先找设计角色。
10. **同页两个历史条目之间的前进 / 后退**由现有闸门按导航处理（dirty 时问一次；继续则页面跟随地址、草稿保留；取消则不变）。前进历史在取消后被截断，属 D275 已知限制。

### 验收

## TORD-06：订单按开票状态筛选

### 现状（main `f5defcc`）

- 订单列表查询（`packages/infra/src/storage/trade-documents.ts:136–148`）支持 `party/cursor/side/from/to`；开票状态在每页查询后计算：`tradeOrderPageInvoicedSql`（:160–163）汇总本页订单行的已开票数量，`tradeOrderInvoicingStatus`（:165–170）判定 none / partial / full，在 :614 写入列表项。

- 列表“开票状态”列改为读存储的状态，取代 TINV-03 验收 3 的“聚合 EXPLAIN”判据（逐页聚合 `tradeOrderPageInvoicedSql` 不再用于列表）。

以下存储口径与已批准的开发方案一致，为**唯一**通过条件（不再保留“逐行数量再派生”的备选）：

1. **迁移 019**（`019-trade-order-invoicing.sql`）：新表 `trade_order_invoicing(company_id, order_id, status)`，`status` CHECK 为 `none|partial|full`，主键 `(company_id, order_id)`，外键指向 `trade_orders`；索引 `trade_order_invoicing_status(company_id, status, order_id)`；禁止删除、禁止改主键的触发器。每张订单恰好一行。
2. **新订单默认 `none`**：`trade_orders` 的 AFTER INSERT 种子触发器写入 `status='none'`，任何订单写入路径都不会漏行。
3. **回填**：迁移 SQL 先为全部已有订单写 `none`，再由 019 的迁移后置钩子对有未作废发票行的订单用 `invoicedOrderLines` + `quantityMicros` + `tradeOrderInvoicingStatus` 计算并更新为 `partial` / `full`（十进制换算不在 SQL 内做）；整体在迁移事务内，失败全部回滚、版本仍为 018。不在应用启动时补算。

- `master.loading`（“正在读取主数据…” / “Loading master data…”）与 `master.error`（“主数据请求失败。请检查连接和目标库配置后重试。” / “Master data request failed. …”）定义在 `ui/master-labels.ts:6,8,86,88–89`，原为科目表页文案。
- 这两个键被全站约 40 处借用：`App.tsx` 的 17 个 Suspense 兜底，以及迁移核对、发票、订单、调整、结算、贸易报表、账簿、期末结账等页面。因此在迁移核对页、发票页等处加载或出错时，界面写着“主数据”，文不对题。
- 全仓检索（含测试、端到端与 `*.md`）没有断言这四句原文。

### 范围与决定（D384）

1. 只改 `ui/master-labels.ts` 中这两个键的中英取值，**不改键名**（改键名会波及 `App.tsx` 与贸易页，与 TINV-07 / TORD-06 冲突）。
2. 定稿文案：
   - `master.loading`：中文“正在加载…”；英文“Loading…”。
   - `master.error`：中文“请求失败。请检查连接和目标库配置后重试。”；英文“Request failed. Check the connection and target database configuration, then retry.”
3. 不改 TSX、组件、CSS 与接口。
4. 键名仍叫 `master.*` 的命名债进候选池，TINV-07 合并后再处理。
5. 不进 DEMO-12 截图，也不列入门禁（D384）。

### 验收

- **E1**：`master-labels.ts` 中四个取值逐字等于上面的定稿文案；`ui.test.ts` 的中英键集合检查通过。
- **E2**：在 `packages/web/test/migration.test.tsx` 追加中英用例（沿用该文件 `render(<App />)` + `#/migration` 的写法），每个用例按以下顺序断言，避免路由 Suspense 兜底（同文案、同 `role="status"`）造成假阳性：
  1. **页面已挂载**：`await findByRole("region", { name })` 找到迁移页 `<section>`（`name` 为 `migration.title`，中文“迁移核对”，英文“Migration reconciliation”），且其中可见页头标题；此后所有断言都用 `within(该 section)` 限定范围。
  2. **请求确实挂起（加载用例）**：`/api/v1/migration` 的 fetch 返回测试持有的未完成 Promise（如手动 deferred），断言 `fetchMock` 已以该路径被调用、且断言时 deferred 尚未 resolve / reject。
  3. **加载断言**：`within(section).getByRole("status")` 的文本逐字为“正在加载…” / “Loading…”；同一 section 内不出现运行卡片（如“待确认” / “Awaiting confirmation”）。用例结束前 resolve 或 reject 该 deferred 并卸载。
  4. **失败断言（失败用例）**：页面按步骤 1 挂载后，让 `/api/v1/migration` 返回非 2xx（或 reject），`await within(section).findByRole("alert")` 文本逐字等于新的 `master.error` 文案；同一 section 内不再有 `role="status"` 的加载提示。
- **E3**：`git grep -n '正在读取主数据\|主数据请求失败\|Loading master data\|Master data request failed' -- packages docs scripts` 无结果（`design/` 中本任务书引用旧文案，不计入）。
- **E4**：`git diff --name-only` 只包含 `packages/web/src/ui/master-labels.ts` 和 `packages/web/test/migration.test.tsx`（如新增测试文件，可再加 `scripts/test-shard-weights.json` 的追加条目）。
- **E5**：Web 全部既有测试照常通过，不修改任何既有断言。
- **E6**：PG-05 按 S10 口径：base 为 PR 实际 base，gzip-9，数字绑定最终送审 head，写入 PR 正文字节表；入口块 ≤ +0.1 kB（预计变小）；CSS 0 B。
- **证据要求（D384，比照 D375 / D377）**：不申请浏览器槽位，以 jsdom 与 E1–E2 中英验收为准。
