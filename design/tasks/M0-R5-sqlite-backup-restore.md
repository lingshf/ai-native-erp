# M0-R5 SQLite 目标库备份与恢复

- 里程碑：M0 评审后续　依赖：M0-R　建议分支：`sqlite-backup-restore`
- **阻塞 M1：否**；**M2 前置门禁**：真实账套迁入目标库之前必须完成

## 背景

M0-15 退役了旧格式的备份/恢复和快照，目前新的 SQLite 目标库没有任何备份或恢复能力。单用户本机使用时，一旦误操作或磁盘损坏，就没有恢复手段。目标库开启了 WAL：崩溃或异常停机后，已提交的数据可能还在 `-wal` 文件里，没有写回主文件。

## 范围

- 沿用现有 storage admin CLI，不新建入口。两个命令都必须显式指定目标库路径，不使用默认值。
- `backup <db> <out>`：用 SQLite 在线备份 API 或 `VACUUM INTO` 生成单个一致的文件（不带 sidecar），服务运行中也可以执行。
- `restore <db> <in>`：离线、独占操作。
  - **排他维护边界**：从第 1 步取得独占开始，到第 7 步（或回滚）结束，全程持有同一个排他维护锁（例如目标库旁的锁文件，服务启动时也检查这个锁，持有期间服务拒绝启动、不会打开目标路径）。边界内任何一步失败都走回滚，结束后才释放锁。
  1. 取得排他维护锁，并确认服务未运行、拿得到 SQLite 排他锁，否则拒绝。
  2. 校验备份文件：`PRAGMA integrity_check`、迁移版本与当前代码一致，否则拒绝。
  3. 用 SQLite 正常打开目标库，执行 `wal_checkpoint(TRUNCATE)`，把已提交数据写回主文件；然后**关闭全部 SQLite 句柄**。checkpoint 或关闭失败就拒绝恢复，不再做后续步骤。
  4. **替换前**确认旧的 `-wal`、`-shm` 已不存在。还存在就拒绝替换，也不手工删除，报告给用户处理。
  5. 把旧库主文件整体复制为带时间戳的 `.bak`（此时是完整单文件、无 sidecar），并校验它能完整打开。
  6. 把备份文件先复制到同目录临时文件，再原子改名替换主文件。
  7. 打开新库做 `integrity_check` 和迁移版本检查，然后关闭。失败就回滚：用 `.bak` 原子改名还原主文件，再验证还原后的库。
  - 失败标准：任何一步失败后，**原账数据完整可恢复**（目标库保持原数据，或可由 `.bak` 完整还原，包括原来 WAL 中已提交的事务）。不承诺失败时各文件字节不变（例如 checkpoint 本身会改写主文件和 WAL）。
- 不做：定时备份、远程存储、增量备份、Web UI。

## 验收标准

- 测试：
  - 备份后修改数据，恢复后数据回到备份时的状态；
  - 在有写入的同时备份，得到的文件一致；
  - 服务运行中（或拿不到排他锁）执行恢复被拒绝，目标库不变；
  - 备份文件损坏或迁移版本不一致时，恢复被拒绝，目标库不变；
  - 目标库带有含已提交数据的 `-wal`（模拟异常停机）时，恢复后的 `.bak` 包含这些数据，可以完整打开；
  - 在 checkpoint 后、改名前模拟失败，原数据仍能完整恢复；
  - 替换前旧 `-wal`/`-shm` 仍存在（例如另有连接未关闭）时，拒绝替换，不删 sidecar，原数据完整；
  - 维护锁持有期间启动服务被拒绝；
  - **改名后验新库失败**（模拟新库校验失败）时自动回滚，目标库恢复为原库，并包含恢复前留在 WAL 中的已提交事务。
- README 写明备份/恢复步骤和“恢复必须先停服务”。CI 绿。

## 性能考虑

在 100 万 GL 行的库上，备份期间热读 p95 仍 ≤ 1s（在 Bench 中手动测一次，结果写进 PR）；备份不长时间持有写锁。
