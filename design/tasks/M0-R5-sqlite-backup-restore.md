# M0-R5 SQLite 目标库备份与恢复

- 里程碑：M0 评审后续　依赖：M0-R　建议分支：`sqlite-backup-restore`
- **阻塞 M1：否**；**M2 前置门禁**：真实账套迁入目标库之前必须完成

## 背景

M0-15 退役了旧格式的备份/恢复和快照，目前新的 SQLite 目标库没有任何备份或恢复能力。单用户本机使用时，一旦误操作或磁盘损坏，就没有恢复手段。目标库开启了 WAL：崩溃或异常停机后，已提交的数据可能还在 `-wal` 文件里，没有写回主文件。

## 范围

- 沿用现有 storage admin CLI，不新建入口。两个命令都必须显式指定目标库路径，不使用默认值。
- `backup <db> <out>`：用 SQLite 在线备份 API 或 `VACUUM INTO` 生成单个一致的文件（不带 sidecar），服务运行中也可以执行。
- `restore <db> <in>`：离线、独占操作。
  1. 先取得目标库的独占访问（服务未运行，且能拿到排他锁），否则拒绝。
  2. 校验备份文件：`PRAGMA integrity_check`、迁移版本与当前代码一致，否则拒绝。
  3. **残留 sidecar 的处理**：如果目标库存在 `-wal`/`-shm`，先用 SQLite 正常打开目标库并执行 `wal_checkpoint(TRUNCATE)`，把已提交数据写回主文件；checkpoint 失败就拒绝恢复，不改任何文件。不允许直接删除 sidecar，也不允许只替换主文件。
  4. 把完成 checkpoint 的旧库整体复制为带时间戳的 `.bak`（单文件、无 sidecar，可直接打开），并校验它能完整打开。
  5. 把备份文件先复制到同目录临时文件，再原子改名替换主文件；替换后确认没有残留 sidecar，打开新库做 `integrity_check`。
  - 任何一步失败：目标库保持原样（或从 `.bak` 原样还原），并报告失败步骤。
- 不做：定时备份、远程存储、增量备份、Web UI。

## 验收标准

- 测试：
  - 备份后修改数据，恢复后数据回到备份时的状态；
  - 在有写入的同时备份，得到的文件一致；
  - 服务运行中（或拿不到排他锁）执行恢复被拒绝，目标库不变；
  - 备份文件损坏或迁移版本不一致时，恢复被拒绝，目标库不变；
  - 目标库带有含已提交数据的 `-wal`（模拟异常停机）时，恢复后的 `.bak` 包含这些数据，可以完整打开；
  - 在 checkpoint 后、改名前模拟失败，目标库或 `.bak` 仍能完整恢复出原数据。
- README 写明备份/恢复步骤和“恢复必须先停服务”。CI 绿。

## 性能考虑

在 100 万 GL 行的库上，备份期间热读 p95 仍 ≤ 1s（在 Bench 中手动测一次，结果写进 PR）；备份不长时间持有写锁。
