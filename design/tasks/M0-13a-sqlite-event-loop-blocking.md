# M0-13a 同步 SQLite 阻塞事件循环：度量与处理

- 里程碑：M0　依赖：M0-13　建议分支：`sqlite-event-loop-blocking`
- 来源：M0-12（[#21](https://github.com/lingshf/ai-native-erp/pull/21)）与 M0-13（[#22](https://github.com/lingshf/ai-native-erp/pull/22)）的百万 GL 行 Bench 中，事件循环最大延迟 362–866ms（`monitorEventLoopDelay`）。PR 评审要求另开任务。

## 问题

better-sqlite3 是同步 API，查询在 Node 主线程执行。试算、报表、结账预览等聚合在百万行库上 p95 约 540–640ms，期间主线程无法处理任何其它请求。单用户也会受影响：同一用户在多个标签页同时发请求（或一个页面并发拉报表和列表）时，后到的请求要排在前一个查询之后，延迟叠加；连健康检查、静态资源、取消操作也要等。现有 Bench 只测了“最新账簿四条热读路径 + 结账预览”的串行延迟，没有测并发排队、未调整（unadjusted）报表、六项对账和靠后分页。

## 目标

1. 补齐度量：并发排队、未调整报表与六项对账、靠后分页。
2. 选**一个**通用方案让主线程不再被 SQLite 长查询阻塞，使事件循环阻塞满足下述预算。
3. 原有路径的 Bench 预算不放宽。

## 预算（设计角色提出）

| 指标 | 预算 | 依据 |
| --- | --- | --- |
| 主线程事件循环单次阻塞（Bench 全程 `monitorEventLoopDelay` 的 max，分辨率 10ms） | **≤ 100ms**；p99 ≤ 50ms | 100ms 是用户感知“即时响应”的常用阈值（Nielsen / RAIL）。并发时，后到请求要多等前一个请求的阻塞时间；阻塞 ≤ 100ms 时，3 个标签页同时请求也只增加约 0.3s，热读仍有余量留在 1s 预算内。剩余主线程工作只有路由、校验、JSON 序列化（≤ 500 行页），100ms 足够。 |
| 轻请求在重查询并发时的延迟（`/api/v1/health` 和一条小列表接口） | p95 ≤ 100ms | 证明重查询不再挡住其它请求。 |
| 并发 3（模拟 3 个标签页同时发 trial / balance-sheet / ledger 首页，循环 50 轮） | 每条路径 p95 ≤ 1500ms，并记录与串行 p95 的差值 | 热读单请求预算是 1s；ubuntu runner 为 4 vCPU，WAL 支持并发读，并发 3 不应接近串行累加（约 1.8s）。 |
| 未调整试算/报表、六项对账（`/reports/reconciliation`） | p95 ≤ 1000ms | 产品热读预算（product-guidelines PG-05）。 |
| 总账明细首页 / 中间页 / 末页（10 万行单科目单月，按游标取第 1、100、200 页，每页 500 行） | 各 p95 ≤ 1000ms，且末页 p95 ≤ 首页 p95 × 3 | 游标分页成本应与页号基本无关；期初与前缀余额由 SQL 重算，靠后页可能退化为 O(偏移)。 |
| 原四条热读路径、结账预览 | 维持原预算（≤ 1000ms / ≤ 2000ms），且 p95 较本任务前回退不超过 10% | 消息传递和结构化克隆有开销，需要量化。 |

## 候选方案与取舍

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. worker 线程执行存储 | 主线程不再加载 better-sqlite3。application 用例在 worker 中执行：1 个写 worker 持有唯一读写连接（与 SQLite 单写者一致，写用例和结账确认的事务内重算都在这里）；R 个读 worker（默认 `min(2, CPU 数 − 1)`，可配置）各持只读连接，执行报表/列表/预览这类零写入用例。主线程只做 HTTP、校验和序列化，用消息把 `{用例, 输入}` 发给 worker 并取回结果。 | 一个机制同时解决所有路径的阻塞，包括今后的新查询；WAL 让读 worker 真正并行，也能缓解多标签页排队。 | 有消息与克隆开销（响应已有界，≤ 500 行/页）；要处理 worker 崩溃、关闭和启动顺序。 | **推荐**，作为唯一通用方案 |
| B. 分块让出 | 用 `iterate()` 逐行读取，每 N 行 `setImmediate` 让出 | 不引入线程 | 无效：主要耗时在单次 `GROUP BY` 聚合的一次 `step()` 内，没法分块；分块还会拆散只读事务快照，破坏报表一致性。 | 否决 |
| C. 只做查询优化（索引、期间余额表等） | 逐条优化慢查询 | 同时降低延迟 | 不能为今后的查询提供上限；期间余额表已在 M0-12 按“不预先设计”的原则推迟。 | 不作为通用方案。A 落地后，若某条路径仍超预算，可以针对该路径做查询优化（限本任务的预算场景），不另立第二套机制 |
| D. 多进程 / 外部数据库服务 | — | — | 违背“本机单用户 SQLite、不过度设计”的原则 | 否决 |

“只选一个通用方案，不并存两套”：A 落地后，主线程对 better-sqlite3 **零调用**，不保留“小查询走主线程、大查询走 worker”的双路径。启动时只做校验的 verifySchema 也在写 worker 中执行。

## 范围

- infra：worker 执行器（写 worker + 读 worker 池）、消息协议（请求 id、用例名、输入、结果或安全错误）、启动/关闭顺序（先停 HTTP，再等 in-flight 完成，再关 worker 和连接）、worker 异常退出时返回统一安全错误（503）并重建 worker；读 worker 使用只读连接（`readonly` + `query_only`）。
- core/application：用例按“零写入读 / 写”分类并注册，供执行器路由；用例代码本身不改语义。
- 边界检查：`better-sqlite3` 只允许在 `infra/src/storage/` 和 worker 入口中导入；主线程入口和 `http/` 导入即失败。
- Bench（只在 nightly/manual 层）：补齐上表所有场景；输出 raw/p50/p95/p99、事件循环 max/p99、并发与串行对比、PASS/MISS；保留原四条路径和结账预览。
- 不做：请求取消（SQLite 步骤无法中途安全打断，仅在客户端断开后丢弃结果）；多用户、连接池调优、余额表。

## 涉及文件

`packages/infra/src/storage/**`、`packages/infra/src/main.ts`、`packages/infra/src/http/**`（只改调用方式）、新增 worker 入口、`packages/core/src/application/**`（用例分类与注册）、`scripts/check-boundaries.mjs` 及其测试、`packages/infra/bench/**`、`.github/workflows/bench.yml`（如需新增步骤）。

## 验收标准

- Bench 结果满足“预算”表全部条目；任一条 MISS 时如实报告，由设计角色决定是否生成子任务，不得改用小库或放宽阈值。
- 主线程不加载 better-sqlite3：边界检查有对应失败用例；启动后 `process.moduleLoadList`/模块解析守卫证实主线程未加载原生模块（选一种做法）。
- PR 层小测试（不用大数据）：在读 worker 中用测试专用 SQLite 自定义函数制造约 300ms 的慢查询，同时请求 `/health`，后者 ≤ 100ms 返回；写 worker 崩溃后下一次请求得到安全 503，随后的请求恢复成功。
- 事务语义不变：写用例仍是单 `BEGIN IMMEDIATE` 事务；报表仍在单只读事务快照内完成；既有 application/HTTP 测试无需改断言即通过（只允许改测试的装配方式）。
- PR 描述给出 Bench 运行链接、上述表格的实测值，以及 CI 时长（PR 层不应增加超过 30s）。

## 性能考虑

本任务即性能任务。结构化克隆开销用原四条路径的前后 p95 对比量化；读 worker 数默认值用并发 3 场景选定，在 PR 描述记录 1/2/3 个 worker 的对比。

## 测试要求

慢查询并发与 worker 崩溃各 1 个 HTTP 层测试；大数据场景只放在 Bench；不重复测既有用例的业务规则。
