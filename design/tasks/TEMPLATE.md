## 现状（main `<sha>`）

每条事实给出 `path:line`、日志或 PR 评论；没有来源的写“推断”。关于现有行为的断言，尤其是否定性断言（“会丢失”“没有”“不支持”），附实现该行为的代码 `file:line`，或检索命令及其结果（S9 回顾行动 7）。肯定性断言（“已有测试覆盖”“沿用某处断言”“某函数已经测量了 X”）同样附该断言的 `file:line`，并写明它在哪个视口、主题、语言下执行；读代码核对，不读 PR 正文（S10 回顾行动 6）。

## 设计决定（产品负责人）

最后一条写“用户可见变化”（PR 正文须有同名一节）：逐条列出界面、接口或行为上用户能看到的变化；没有的写“无”并说明（例如“只改内部结构，入口块变小”）。

## 导航与历史

任务涉及浏览器历史、导航拦截或全局事件监听（`popstate`、`hashchange`、`beforeunload`）时必填（路线图 §5 设计文档自查 9，S9 回顾行动 1）；不能只写结果：

- **机制**：例如“只用 `pushState`，不调用 `history.go`”；
- **注册位置与顺序**：监听器在哪个模块、何时注册，相对 `HashRouter` 等其他监听器的先后（例如“模块求值时注册，由 `App.tsx` 静态导入，早于路由器挂载”）；
- **可接受的限制**：例如“取消会截断前进历史”。

不涉及时写“不适用”并说明（例如“只改组件状态，不改地址、不加监听”）。

## 验收标准

编号列出；每条都能用测试、日志或 `git diff` 判定。每条写明证据类型与平台（MCF-15），例如：

| 编号 | 验收 | 证据类型 | 平台 / 环境 | 来源 |
| --- | --- | --- | --- | --- |
| 1 | … | 单元或集成测试 / 真实 Chrome 取证 / 基准 / 日志 / `git diff` / 人工核对 | Linux CI（PR 或 main Full）/ Windows 本机 / 两者；浏览器任务写视口、主题、语言 | 测试文件与用例名，或取证步骤；新增的写“新增”及计划的名字 |

同一条在不同平台证据不同时分行写；只在一个平台取证的，写明另一个平台为何不需要。契约变化只在响应 schema 上增加字段；请求 schema 与其他共享的严格 schema 不改，除非任务明确要求并写明兼容验收。

## 性能考虑

每份任务书必填（[产品准则](../product-guidelines.md)“性能考虑”，PG-05）。逐项写，不适用的写“不适用”并给理由：

- **规模 / 热点**：数据量级（如“1 万张订单、每张 1–20 行”）与一页上限，给出基准或夹具的 `file:line`；
- **读写路径与索引**：走哪个索引（迁移 `file:line`），是否新增索引；
- **查询次数**：每次请求 / 每页的查询次数，写明与页大小无关；不允许逐行查询；
- **分页**：keyset 还是偏移，聚合是否只覆盖当前页；
- **事务 / 锁 / 缓存边界**；
- **前端开销**：额外请求、渲染量；无 UI 写“不适用”；
- **预算与验证方式**：预算数字（如热读 p95 ≤ 1s），定数前先在实际 base 上对方案试算一次，写出试算数字与命令（S12 回顾行动 5）；拆分任务的试算包含要搬走的命令与闭包，不只抽组件与 Hook（D461）；用哪个基准、base 与 head 怎样对比；不测时写“未测”与理由。基准在合并 main 后或每晚 CI 运行，不进入 PR 快速套件；不为此加重复测试。
- **首屏比对**（拆分任务默认，S14 回顾行动 3，D460）：首屏只有预加载顺序不同时，按 [D454](S14.md#s14-期间决定d451d458) 的四条判定视同 ±0：① 预加载集合相同；② 原始字节 ±0；③ `m.f` 表与每个 `__vite__mapDeps` 列表各自排序后 base 与 head 文本相同；④ 屏蔽哈希后的 gzip-9 差 ≤ ±10 B。其他差异按任务书条款判定，不再逐任务裁定预加载顺序的例外。

## 可读性

每份任务书必填。口径只按[路线图 §5 完成定义“可读性” ①–⑥](../roadmap.md#5-团队流程)，本节不另写数字：

- **热点文件**：本任务会改动的文件中，按路线图 §5 ③ 判为热点的逐个列出（附实测行数），写明本任务允许的净增（计法与默认上限见 ③；需要突破时写理由或先拆分）；
- **结构要求**：新增逻辑放在哪个模块 / 函数，是否需要先抽取辅助函数（② ④）；
- **搬移类任务**：写明哪些代码属于“纯搬移”（只受 ③ 约束）以及证明文本不变的方法；
- **验收**：PR 正文“可读性”一节按路线图 §5 的要求填写，评审可据此退回。

只改文档或配置的任务写“不适用”并说明。

## 设计阶段质量项

自 D555 起每份任务书必填（[团队章程 §3](../team-charter.md#3-完成定义dod)）。每项写 `applicable` 加内容，或写 `not_applicable` 加理由。适用与否按改动触及的范围与风险判断（D557）：

- **纯重构**（不改行为）只有在不触及任何页面、也不触及有性能预算的路径时，才可把 UI 与性能标 `not_applicable`，理由写具体的无影响依据（例如“只改 core 纯函数，无页面引用，不在任何预算覆盖的路径上”）。“输出逐字节不变”本身不足以免除 UI 或性能项。
- **页面拆分**（如 REFAC-33）：UI 项适用，写明要提供的真实渲染与交互证据（焦点、键盘、状态切换、窗口宽度），由 QA 核对。
- **触及已有性能预算的路径**（如 bundle-measure 覆盖的体积）：性能项适用，引用该预算并写明测量方法（路线图 §5 R7）。
- 功能边界一项始终须填写。
- 实质性的 `to_confirm`（会影响设计取舍的预算或口径）未确认前，本任务不算就绪、不派发；只写负责人不够。

- **UI**：主路径与信息层级；沿用的现有组件或设计参考（`design/ui/` 或页面 `file:line`）；成功反馈与空、加载、错误、禁用状态；窗口宽度；键盘与焦点；中英文；红绿主题；教学模式开关。
- **功能边界**：模块或组件职责；接口与依赖；数据流；读写与状态归属；失败边界。
- **性能计划**：关键路径；工作量假设（数据量、并发、设备）；预算与验证方法和环境，可引用上文“性能考虑”。预算未知时写 `to_confirm` 和负责人，不编造数字；实质性的 `to_confirm` 阻断就绪（见上）。
- **类型**：新写或实质改动的 TS 用原生类型；纯 `.js` / `.mjs` 脚本用合法 JSDoc。

## 证据要求

- 真实 Chrome 与 E2E：按[路线图 §5 UI PR 证据清单](../roadmap.md#5-团队流程) 1–10 项，请求评审前逐项勾选，包括：
  - 第 7 项：断言对照实际渲染与 schema 字段位置，列出“断言 → `file:line`”；数量 / 行数类断言另列产生数据的 seed 语句 `file:line`；中止后改过产品代码时，逐条复核取证工具中引用该行为的判定；
  - 第 8 项：取证先 build，并断言 dist 比 HEAD 新。
  - 第 9 项：每个 390 px 步骤断言页面级 `document.documentElement.scrollWidth <= window.innerWidth`；截断类判定按实测行距设容差，不用 `scrollHeight > clientHeight`。
  - 第 10 项：逐步写明等待条件（目标状态本身，带墙钟上限），并标明该步属于必发请求的路径（请求 200 → 旧行消失 → 新行出现 → 快照）还是可能走缓存的路径（直接等目标 DOM，需要时断言未发请求）。
- PG-05：base 为 PR 实际 base；数字绑定到最终送审的 head，与取证 head 分开写。
- **只能由真实 Chrome 证明的验收项**（S9 回顾行动 2）：逐项列出（布局与宽度、页面横向溢出、监听器顺序、首键 / 首次安装时机等），每项对应一条 `*.slow.test.*` 用例或取证步骤（写出文件与函数名）；mock / jsdom 测试不能替代。几何类验收按视口逐行写成下表（S10 回顾行动 5，路线图 §5 设计文档自查 10）：同一项在不同视口分行；固定阈值写明设计依据适用于哪个视口，其他视口用“前后相等 / base 与 head 一致”之类的比较；“来源”写用例或取证步骤的文件与函数名（新增的写“新增”及计划的名字），沿用现有断言的写 `file:line`。

  | --- | --- | --- | --- |
  | 390 | 页面级 `scrollWidth <= innerWidth` | 必须成立（路线图 §5 证据清单 9） | … |
  | 1440 | … | … | … |
- **带数值的视觉要求写明测量对象的两端**（S12 回顾行动 4）：例如“卡片头底边 → 首个字段标签顶边 ≥ 16 px”，不写“留白约 16 px”；Demo 与取证脚本只按任务书写的对象测量。
- **证明条款的可行性**（S13 回顾行动 4，路线图 §5 设计文档自查 11）：要求开发“证明”的每条验收（等价、字节、耗时、能拦住某类错误等），送审前在实际 base 上把证明方法跑一次，或确认所需工具、数据与观测点都已存在；在“现状”或本节写出命令与结果。做不到的改写成可判定的形式，或注明“推断”及补证的人与时点。
- **证明附原文**（S13 回顾行动 6）：PR 正文附脚本原文与未截断输出，或链接到固定修订；只写结论和计数不算附证据。
- **门禁的“无法判定”**（S16 回顾行动 6，路线图 §5 设计文档自查 14）：门禁类验收除“通过”“失败”外，写出“无法判定”（查询出错、输入缺失）的结果与退出码或处理，默认按失败处理。
- **数字附原文**（S15 回顾行动 1）：PR 正文出现的字节、耗时、计数，不论本任务书是否要求，都附原始输出；比对脚本的阈值引用决定原文。
- **构建来源**（S14 回顾行动 1，D460）：有构建产物比对（字节、耗时）的任务，PR 正文附“构建来源”块：完整 base / head SHA；Node / npm / OS；两侧相同的 lockfile blob（`git rev-parse <sha>:package-lock.json`）；干净工作区与两侧相同的命令；产物摘要。缺少时评审标为“待证据”。**干净须可查**（S17 回顾行动 3，D487）：在新建的分离 worktree 中、分别在确切的 base 与 head SHA 上构建，附 `git rev-parse HEAD` 与空的 `git status --porcelain` 原文；产物摘要写完整、不截断；stash 或改过的工作区得到的构建不算。**Web 打包字节一律用入库脚本**（MEAS-01，S20 起）：用 `node scripts/measure/bundle-measure.mjs --base <40 位> --head <40 位> --work <新目录> <预算参数>`（用法与口径见 [`scripts/measure/README.md`](../../scripts/measure/README.md)），它在两个分离 worktree 中构建并打印上述全部来源字段；PR 正文附完整输出、退出码与脚本所在的提交 SHA，不再附临时测量脚本。任务书只写预算参数（manifest 键与上限）；哈希掩码按 D502 用 `-HASH`。
- **测试在满载下的耗时**（[S20 回顾行动 6](../reviews/S20-retro.md#行动项汇总)，#298 M5）：新增或改动测试的任务，读构建产物、压缩、哈希、构造大型不可变 fixture 等昂贵准备每个测试文件只做一次（`beforeAll` 或共享结果），边界用轻量断言；用例之间须隔离的状态（如渲染整页、查询缓存、`sessionStorage`）仍按用例准备，不为省时共享；PR 正文附目标测试文件在默认超时下的耗时（vitest 汇总行原文，改动已有文件的附 base 与 head 两侧）；单个用例 > 2 s 的写明原因；不靠加大 `timeout` 或重试通过。
- **chunk 归属与首屏预算**（[S22 回顾行动 3](../reviews/S22-retro.md#行动项汇总)，D520 的推广）：改动会进打包产物的任务，按 base 实测（`bundle-measure.mjs` 构建出的 `dist/.vite/manifest.json` 与导入关系）列出每个被改文件落在哪个 chunk（首屏 / 某路由 / 共用 chunk），写出依据；首屏预算单独一行，与路由、chunk 预算互不矛盾（被改文件在首屏 chunk 中时，首屏不能写 ±0）。
- **本机全量 web 测试**（S22 回顾行动 4）：送审时本机全量 web 测试一律用 `npx vitest run --project web`，附汇总行原文；有失败时逐个列出失败的文件与用例，并附只对这些文件的串行重跑原文（`npx vitest run --project web --no-file-parallelism <失败文件…>`）；不得自行更换并发参数而不说明。
- 不需要真实 Chrome 的任务写明理由，例如“只改注释，构建产物字节不变”。
