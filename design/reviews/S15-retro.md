## 议题 1：待证据仍是构建来源与原始输出

- **发生了什么**（观察）：三轮待证据，与 S14 次数相同：
  - #251：比对脚本把其他路由的噪声阈值写成 ±10 B（D462 是 ±4 B）；“保留 CSS 摘要相同”的代码实际只比较了字节数；
  - #254：任务书写明“不做字节比较，不需要构建来源”，PR 正文却报告了首屏字节变化，评审因此要求补两侧干净构建、产物摘要与比对脚本；
  - #256：第一组构建来源齐全，但“重复构建一致”“+873 B 中间测量”“四次运行一致”“本地 331/331”只有结论，没有原始输出；保留 CSS 数写 8，比对输出是 12。
- **根因**：
  - 模板只规定“任务要求字节比较时附构建来源”。PR 正文主动报的数字（#254）和附带说法（#256）不在这条规则的范围内，开发写了，评审照样要核。
  - 比对脚本是每个 PR 现写的，阈值与比较方式没有对照决定原文（#251）。
- **改进**：
  - 行动 1：凡 PR 正文出现字节、耗时、计数这类数字，就适用“构建来源 + 原始输出”，不论任务书是否要求；不想附证据就不写这个数字。

## 议题 4：时段预检被本机其他进程卡住

- **发生了什么**（观察）：
  - 17:47–17:50Z，申请方手动采样 12 次，全部 counted>0；计数的是其他 ai-native-erp 会话的 node / vitest / chrome-headless-shell（#258 `run-through.md` §6）。
  - D468：真实时段改用 `slot-run` 自带的预检等待（连续 6 次 0，最长 15 分钟，不重试）。这次预检超时：68 次采样里没有一次连续 0（D470）。
  - 协调者随即开了全会话静默窗口 D470。用户的另一个项目仍在启动进程，DEMO-15 继续受阻；D471：取图推迟，tag 等 DEMO-15。
  - 采样明细没有归档：手动采样的输出按 slot 规则不入库，超时那次的日志也没进 #258。下面关于“哪些进程被计数”的分析，只有其他 ai-native-erp 会话那部分是观察，其余是推断。
- **根因**（按 [路线图 §5“进程采样规则”](../roadmap.md#5-团队流程) R2 分析）：
  - 现行规则**已经**排除有外仓证据的进程：SR-C2 逐层上溯，最近一层只有其他仓库的路径证据时判 SR-X1。v0.12.0–v0.13.1 的 `slot-summary.log` 中，`debate-coach`、`income-statement-node` 等仓库的 node / cmd 都按 SR-X1 排除了。所以“外仓进程不计数”不是新规则。
  - 仍会计数的有两类：
    1. 其他 ai-native-erp 工作区的进程，有本仓库证据，按规则计数。这一类协调者能管：D442 要求各会话停本地 node。
    2. **归属不明**（SR-C3）：整条祖先链上没有任何仓库路径的进程，例如从非 git 目录、全局 `npx`、用户目录下的工具或服务拉起的 node，或者命令行读不到的进程。（推断）用户的另一个项目如果不是 git 仓库，或从全局位置启动 node，它的进程就落在这一类，按 SR-C3 计数。协调者对这类进程既不能通知，也不能停。
  - R2 把“归属不明”一律计数，是为了让预检更严（路线图表中 SR-C3 的“已知代价”）。在只跑本项目的机器上，这个代价很小。在多项目并行的机器上，它让预检可能无限期等待；D468 又规定不重试，结果就是一直等不到时段。
- **改进**：见行动 5，以下三个方案供协调者决定：

  | 方案 | 做法 | 好处 | 代价 / 风险 |
  | --- | --- | --- | --- |
  | **A（建议）：R3“只计本仓库”** | 时段预检与运行中采样只计数有 ai-native-erp 正向证据的进程（SR-C2 判为本仓库），以及监听时段端口（如 4203）或命令行含本次临时账套目录的进程。“归属不明”改为新排除规则 **SR-X6**：不计数，但每次采样把 PID、进程名、命令行、可读的 cwd 写入 `processes.tsv` 与排除日志。开跑前加一条硬检查：时段端口未被占用 | 时段规则保护的是本仓库的端口、账套与工作区不被干扰，这些只有本仓库的工具会碰；端口冲突由硬检查兜住。其他项目的进程只影响 CPU，而 D440 / D441 只把“截图是否拍对”判为失败，CPU 抖动不会让 Demo 误判。预检从“可能无限期等待”变为可预期 | 本仓库工具若从工作区外、且命令行不带任何本仓库路径启动，会被漏计（推断：本仓库的 npm / vitest / vite 都从工作区 cwd 启动，这种情况很少）。缓解：SR-X6 全量记日志，评审可复查；D442 对本机各会话的停用要求不变 |
  | B：维持 R2，靠静默窗口 | 每次时段前由协调者开全会话静默窗口（D470） | 规则不变，不需要开发 | 管不到不归协调者管的进程（用户的其他项目），本次已经证明会无限期阻塞 |
  | C：专用机器或 CI 取图 | 在没有其他项目的机器（或 Windows CI runner）上跑 Demo | 彻底隔离 | 需要搭环境；现有 PowerShell runner、截图脚本与本机路径耦合，工作量最大。作为长期候选 |

  - 选 A 的理由：方案 A 只放宽“归属不明”这一类。它不放宽本仓库进程（仍计数），也不放宽外仓进程（本来就不计数）。按“采样规则改动须有决定编号、写入路线图并升版本号”的要求，作为 R3 落地，不需要在时段内临时豁免。
  - 例子中“采集期间忽略 ai-native-erp 工作区以外的 SR-X1 外仓进程”，现行 SR-X1 已经做到。真正卡住预检的是 SR-C3，所以 R3 改的是 SR-C3 的去向。

## 议题 5：演练记录与 RC 数字仍要评审纠正

- **发生了什么**（观察）：
  - #258 的演练记录被打回 2 次：桩模式下 runner 用 `node -e` 替换了步骤，记录却说演练了生产用的 `powershell.exe` 子进程（模板第 13 条）；两个 PowerShell 脚本的哈希前缀与归档脚本的 git blob 对不上。
  - #257 RC 被打回 1 次，其中一点是入口 −82 B 没写“屏蔽哈希 gzip-9”口径。#253 写入的规则在 RC 首轮评审前约 35 分钟才合并。
- **根因**：
  - `-Stub` 只验证 runner、预检与构建，不运行真实步骤，但模板没写清它证明什么、不证明什么，记录者把它当成了完整演练。
  - 脚本哈希是在本地副本上算的，不是取自 git blob。
  - RC 的数字是转述，没有原样引用来源 PR 原表中的那一行。
- **改进**：
  - 行动 4：Demo 模板写明 `-Stub` 证明与不证明的内容（不运行步骤脚本，不经过 `powershell.exe` 子进程）；脚本哈希一律取 `git rev-parse HEAD:<path>`。
  - 行动 6：RC 中的体积、耗时数字直接引用来源 PR 原表的那一行（链接到评论或文件行），连同“产物 + 口径”一起抄，不转述。
