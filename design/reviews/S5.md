### 议题 1：D131 改为 D133，S5 累计 CSS +413 B

- **发生了什么**：S5 计划只给 S5-a..f、S5-i 定了“合计 ≤ +0.3 kB”。#125 评审发现累计已到 +535 B（扣除 D112 后 +313 B），超过上限（[评审](https://github.com/lingshf/ai-native-erp/pull/125)）。协调者先定 D131，要求 S5-g 做到 S5 累计净减少；#126 实测删掉整个 `styles.css` 也只能到 13,587 B，仍高于起点 13,259 B。于是改为 D133：S5-g 相对 merge-base 减少，S5 累计扣除 D112 后 ≤ +0.3 kB。#126 实测相对 merge-base −122 B，累计 +413 B（扣除 D112 后 +191 B）。
- **来源（本次实测）**：在临时 worktree 中，对每个 S5 合并提交执行 `npm run build -w packages/web`，然后对每个 `.css` 资产做 zlib gzip level 9，去掉 hash 后按文件名配对。起点、S5-e 后、S5-g 后的合计分别是 13,259 / 13,794 / 13,672 B，与 #125、#126 的评审数字一致。

  | 合并 | 任务 | 本步 | 累计 | 变化的文件 |
  | --- | --- | --- | --- | --- |
  | `f083e97` | S5-b #112 | +57 | +57 | Migration +51，components +6 |
  | `08cd0a2` | S5-c #113 | +75 | +132 | components +35，TradeReports +14，trade-settlements +18，TradeInvoices +8 |
  | `32e9b61` | S5-h #117 | 0 | +132 | — |
  | `ce7a48f` | S5-f #115 | +31 | +163 | components +19，index（外壳）+12 |
  | `7d62fe5` | S5-a #118 | +222 | +385 | Journals +222（D112） |
  | `045fa59` | S5-d #120 | +5 | +390 | TradeOrders +5 |
  | `90569f7` | S5-i #122 | +42 | +432 | components +42 |
  | `2aaa610`、`7a142a3` | FOCUS-01、FLAKE-02 | 0 | +432 | — |
  | `c5c9224` | S5-e #125 | +103 | +535 | ledger +57，PeriodClose +46 |
  | `6c8724b` | S5-g #126 | −122 | **+413** | index（`styles.css`）−122 |

  - 页面和组件新增的类规则共 +535 B，删除全局规则只收回 122 B。其中 `Journals.css` 一项占 222 B，`components.css` 合计 +102 B。
  - 收回得少，原因是选择器长度：元素选择器很短，gzip 下几乎不占字节；同一组声明改写为多个页面限定的类选择器后，选择器本身才是新增的字节。#126 的全删实验说明，`styles.css` 剩余的声明最多还能收回约 85 B（13,672 → 13,587），所以 UI-11d 之后累计仍会在 +300 B 左右。
- **根因**：S5 计划定 +0.3 kB 上限时，没有先估算“复制到页面”的总量，也没有估算“删除全局规则”最多能收回多少，只按每个任务的预算相加。D131 的目标在 #126 的全删实验中都达不到。
- **改进动作**：
  - 规则（负责人：设计角色；落到[路线图 §4](../roadmap.md#4-ci-与测试策略设计角色牵头)）：跨多个任务的累计字节预算，立项时必须附可行性估算。做法是在一个只取证、不提交的构建中模拟目标终态（如全删实验），用其 gzip 结果作为上限依据；做不了估算的，不写累计硬门槛，只写每个任务的预算。
  - 设计角色每次同步任务表时，对有累计预算的 Sprint 按上表口径追加一行，不再等评审发现超限。
- **建议：是否把“+413 B 的来源与瘦身”立为任务**：
  - **来源分析不必另立任务**：上表已逐个合并给出来源，可供 Sprint 评审直接讨论。
  - **瘦身不建议立为 S6 任务**。理由：
    - +413 B 约占 CSS 合计的 3%。本产品只在本机 loopback 运行，单用户，这个量级的加载差异用户感知不到；PG-05 也只按任务预算验收。
    - 最大的单项是 `Journals.css` +222 B，D112 已批准。要缩小它，就得把凭证 / 业务事件页的限定选择器合并为共享组件类。这会改 `.tsx` 的类名和组件边界，与 S6 的 UI-11a、FOCUS-02、UI-11c 同在 web-ui:journals，风险和取证成本都高于收益。
    - `components.css` 的 +102 B 来自 S5-b / c / f / i 四个任务各自补的共享组件规则，按 D77 本就应写在组件层；其余 7 个页面文件各 ≤ 57 B。
  - **替代做法**：不立任务，在 backlog 记一条观察：以后凭证页做结构性重构时，顺带合并重复选择器，以上表为基线。若 Sprint 评审仍要瘦身，再由设计角色立任务，并按上面的新规则先做可行性估算。

### 议题 2：真实 Chrome E2E 独占时段的排队成本

- **发生了什么**：#115 在 `c2f0310` 上的两轮本机 E2E 失败（FLAKE-02 的来源）之后，协调者从 D115 起改为独占时段：同一时间只有一个开发 session 能跑真实 Chrome E2E、Playwright 截图或 vitest slow，其他 session 暂停这几项，编辑、单测和构建照常；D118 要求每个时段的首尾都记录 `rev-parse` 与 `status`，开跑前连续两次确认外部进程为 0，运行中每 10 s 采样一次。此后时段依次给了 #115 → S5-a → S5-i → FOCUS-01 → FLAKE-02 → S5-e → S5-g，例如：
  - FLAKE-02 在 19:45Z 排队，20:37Z 拿到时段（约 52 分钟）；
  - S5-e 在 20:03Z 派发，20:43Z 拿到时段（约 40 分钟，其中一部分是本来就要做的准备工作）；
  - #123 的评审修改期间，时段在 FLAKE-02 手里，只能用已有的日志和产物改正文。
- **根因**：
  - 本机只有一台机器跑真实 Chrome。各 session 同时跑时是否互相干扰（端口、临时目录、Chrome 进程、CPU），**没有证据**：FLAKE-02 的两项故障原因未知。独占时段是在没有证据时的保守选择，本身合理。
  - 每个 UI 任务都要在精确 head 上跑一次完整的 `trade-gui-*` 与 `migration-gui.slow`（6 个文件 / 13 个用例），外加截图和探针，所以每个时段都不短。
  - 时段靠协调者逐条消息派发和收回，排队顺序和结束时间都不在任务表里。
- **改进动作**：
  - 调查任务 [E2E-01](../tasks/E2E-01-concurrent-e2e-interference.md)（负责人：开发；S6 B 线最后一项）：先静态核对各套件是否共用端口、临时目录和 Chrome 用户目录，再按预先写明的次数，对照串行与两个 worktree 并发的运行。结论交协调者决定是否放宽独占时段；没有证据之前，独占时段不变。
  - 规则（负责人：协调者；落到[路线图 §5 工作区隔离](../roadmap.md#5-团队流程)）：独占时段写成一条规则，内容取 D115 / D118，即谁持有、首尾记录、进程预检与采样、结束时报告；协调者在派发消息中给出排队位置。
  - S6 排期时，每条泳道里需要真实 Chrome 的任务尽量错开开工时间，见 S6 计划。

### 议题 3：FLAKE-02 两项故障原因仍未知

- **发生了什么**：#121 合并的是默认关闭的 JSONL 诊断（`ERP_E2E_DIAG=1` 时才开启，D126），以及一次预先定好次数的 5 次实验：
  - **option 空列表**：5/5 通过。诊断**证实** `navigate()` 会在期末页渲染前返回：10 次 `setUp`（5 次 × en/green、zh/red）中有 2 次，返回时 hash 已是 `#/period-close`，`main h2` 仍是旧页标题（“Runtime status” / “运行状态”）（#121 描述）。不过每次选项都在 ≤ 0.65 s 内出现，没有复现 10 s 全空。
  - **afterAll 超时**：5/5 通过，30 个 suite 的 teardown 都在 15 s 内完成；耗时集中在 smoke 的 `browser.close()`，为 2.4–8.7 s。
  - 两项都是**未可靠复现、原因未知**。
- **根因**：未证实。能确定的只有两点：`navigate()` 的就绪条件太弱，命中旧页标题也算就绪；`browser.close()` 耗时波动大。前者能解释“提前返回”，不能解释 #115 第 2 轮 10 s 内一个 option 都没有；后者只是推断可能超过 15 s。诊断开启时多了浏览器往返和写盘，采样节奏变了，这 5 次的数据只作观察（D126）。
- **改进动作**：
  - 任务 [FLAKE-03](../tasks/FLAKE-03-navigate-target-page-ready.md)（负责人：开发；S6 B 线）：把 `navigate()` 的就绪条件改为目标页自己的标题或标志元素。这是已证实的测试缺陷；新条件比原条件严格，符合 D11，不加时、不重试。PR 不得宣称修复了 option 空列表或 teardown 超时，两项仍记为“原因未知”。
  - 规则（负责人：开发执行，评审核对；落到[路线图 §5 偶发失败](../roadmap.md#5-团队流程)）：之后任何本机或 Full 运行再出现这两种失败，保留日志和 trace，并在同一 head 上用 `ERP_E2E_DIAG=1` 做一次定向诊断运行，产物附到 FLAKE-02 任务文件的观察中（由设计角色同步）。不重跑到通过为止。
  - 诊断插桩默认关闭（D126）写入路线图 §5：诊断不得改变默认路径的时序，评审时须核对默认路径的代码与原来逐表达式一致。

### 议题 4：评审打回的轮次与共性原因

  | --- | --- | --- | --- |
  | A. 验收证据不全或来源未绑定 | 8 | #112（1）、#113（2）、#115（1）、#118（2）、#122（1）、#123（1） | 缺 `ERP_E2E_ARTIFACTS` 截图或 base/head 配对图；日志早于 commit 创建，或没有证明来自干净的精确 head；PG-05 记录与正文不一致；计数与进程归属写错 |

  - **C**：模板中的命令只跑过失败分支或模拟，没有用替身跑完整的成功分支。
