## 议题 1：DEMO-22 的 RC 退回 3 轮，证据不全

**发生了什么（观察）**

[#319](https://github.com/lingshf/ai-native-erp/pull/319) 3 次打回（[6033643731](https://github.com/lingshf/ai-native-erp/pull/319#pullrequestreview-6033643731)、[6033686652](https://github.com/lingshf/ai-native-erp/pull/319#pullrequestreview-6033686652)、[6033738959](https://github.com/lingshf/ai-native-erp/pull/319#pullrequestreview-6033738959)），每轮都不重开窗口、不改原始日志。打回点分三类：

- **时刻缺原始记录**（取证缺口，已接受）：放行时刻、步骤 1 与窗口快照命令的启动时刻只存在于 shell 屏幕上的 `Get-Date` 输出，没有存文件；第 1 轮送审时把它们当作事实写进 run-through，第 2 轮被指出是事后转述，最终作废，只能用快照帧界定范围（run-through 第 83 行）。关窗时刻 20:21:46.733 取自 `gate.stop` 的文件创建时间（第 81 行），不是 S21 行动 1(b) 规定的“关窗后立即写时间的命令”。
- **清理前清单不全**（证据格式）：账套清单齐全，但 D492 全产物清单第 1 轮缺失，第 2 轮缺原路径、字节数、行数与清理前哈希，第 3 轮仍缺行数，且开窗前的产物（`npm ci` 与构建日志、`gate-pre.tsv`）不在清单里；原件哈希与入库 blob 哈希没有分开；文件数写成 20（实为 21）。
- **K2 选择器缺陷**（取证缺口，D521）：capture 的 `tbody input` + `hasNot: [type=checkbox]` 没有排除任何元素（`hasNot` 看子孙，`input` 没有子孙），`.first()` 取到了行首 checkbox，`inputValue()` 返回默认值 `on`。窗口内“金额不变”的断言因此比较的是 `on` 与 `on`，恒真（run-through 第 115–116 行）。第 1 轮评审发现；按 D521 不重开窗口，改由 TLIST-06 S3 证明。
- 另有自查不全：D495 / D511 的 `git diff --check` 全量 exit 2（21 个文件，都在 `logs/`）没有披露，命令用了 `HEAD` 而不是完整 SHA；`git grep` 没有原样输出；缺发布证据索引。三轮里都有这一类。

**根因（推断）**

- S21 行动 1(b) 写了“关窗后执行写时间的命令并存进日志”，但没有覆盖放行与各步骤启动的时刻；执行时在交互 shell 里看时间，屏幕输出没有落盘，事后无从补。
- D492 清单是在送审后按评审意见逐项补的，没有一个“清理前必须产出的清单格式”可以照着填；每轮补的是上轮指出的字段，没有一次性对齐模板。
- S21 行动 2 只要求窗口外验证**焦点路径**；K2 读的是**值**，不在行动 2 的范围内。capture 中取值的定位器没有先断言元素的角色与可访问名称，所以选错元素也不会失败。

**改进**：行动 1、行动 2。

## 议题 2：N7 预算条款自相矛盾（D520）

**发生了什么（观察）**

TSET-01 任务书 N7 同时要求“首屏 ±0”和“`trade-labels.ts` 所在 chunk ≤ +400 B”。`trade-labels.ts` 在首屏 chunk 里，加标签键必然让首屏增加，两条不能同时满足。开发在 [#320](https://github.com/lingshf/ai-native-erp/pull/320) 实测首屏 +170 B 后提出，协调者代定 D520：本任务首屏按 ≤ +400 B 计，D454 的通用规则不变，今后新增标签键的任务书要单独写明首屏预算。

**根因（推断）**

起草 S23 计划时，我按 D454 的通用写法照抄了“首屏 ±0”，又按文件所在目录给了路由预算，没有在 base 上实测 `trade-labels.ts` 落在哪个 chunk。#318 两轮评审也没有核对这一点，因为任务书没有写出 chunk 归属，评审无从对照。

**改进**：行动 3。

## 议题 3：本机并行跑 web 测试出现时间敏感的超时

**发生了什么（观察）**

- [#311](https://github.com/lingshf/ai-native-erp/pull/311)（REFAC-12）送审说明：默认并发下 `trade-reports` / `trade-invoice-detail` 出现 1–3 个超时，`--maxWorkers=4` 或 `2` 时通过。
- [#316](https://github.com/lingshf/ai-native-erp/pull/316)（TLIST-06）：`journals` / `trade-orders` 在负载下偶发超时。
- [#320](https://github.com/lingshf/ai-native-erp/pull/320)（TSET-01，S23）N4：本机 16 核，`npx vitest run --project web --maxWorkers=8` 连跑 3 次都是 exit 0、`Tests  384 passed (384)`；默认并行（`maxWorkers` 16）出现间歇失败，head 上一次为 `1 failed | 383 passed (384)`，base `fcf2db8` 上同一命令连跑 3 次为“2 失败、全过、全过”。失败用例分散在不同文件（`trade-period-admission`、TINV-06 / TINV-07 等），base 与 head 上都出现过。
- main Full 同期 8 / 8 绿，没有出现这些失败。

**根因（推断）**

本机同时跑着其他 session 的 node 进程，并行 worker 抢 CPU 时，jsdom 渲染加网络桩的耗时可能超过断言等待的默认上限；失败用例分散在多个文件，不能断定都是同一种 `waitFor` 失败。这是推断：没有在空载机器上对照，也没有记录当时的进程负载。每个 PR 各自换一种并发参数，送审证据的口径不一致，评审需要逐个判断“是否与改动有关”。

**改进**：行动 4；候选池加 FLAKE-09。

## 议题 4：S21 行动 3 没有达成，DOC-22(b) 退回 3 轮

**发生了什么（观察）**

S21 行动 3 要求“回顾行动写成模板或清单条款时，每条技术断言先实测”。[#317](https://github.com/lingshf/ai-native-erp/pull/317) 3 轮打回都落在这一点：第 1 轮把“建停止文件”写成必然 exit 0（实际还有 8 / 9）、T1–T4 缺原始输出；第 2 轮 T2 的 `Start-Job` 块内 `$D` 不继承外层变量，所贴命令复现不了日志；第 3 轮示例命令路径未加引号，含空格路径被拆成多个参数。

**根因（推断）**

PR 正文附了实测，但实测用的命令与模板里写给读者的命令不是同一段文本：实测时路径不含空格、变量在同一作用域，模板里的写法没有被原样执行过。“附实测”被理解成“附一次运行结果”，而不是“模板中的每条命令原样执行一次”。

**改进**：行动 1 的“证据命令从入库脚本运行”同样适用于模板示例；不另立行动，S23 检查时按 S21 行动 3 的完成标准继续核对。
