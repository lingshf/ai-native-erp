## 议题 1：时段产物在清理前没有记录哈希（D492）

- **发生了什么**（观察）：#286 第 1 轮要求附清理前的证据清单。版本管理此时已清理临时目录，窗口内的日志路径、SHA-256、行数，两次 `npm ci` / build 的控制台输出，以及其他临时文件都无法再取得。协调者按 D492 接受为缺口：证据以入库的日志与截图字节、退出码和 PR 中引用的关键行为准，不重跑。
- **根因**：
  - Demo 模板“日志入库”一节**已经要求**写完日志后、清理临时目录之前记录日志路径、SHA-256 与行数（`docs/demo/TEMPLATE.md`，`d519bb4` 第 126 行）。D492 是这一检查被漏做，不是模板没有规定；而模板只覆盖日志，`npm ci` / build 控制台输出与其他临时文件不在其内。
  - 入库产物的哈希还混淆了两种字节（#286 第 2 轮：`processes-real.tsv` 写的是工作区检出文件的哈希，不是入库 blob 的字节）：清理前的原始字节与入库后的 blob 字节是两份证据，口径没有分开写。
- **改进**：
  - 行动 1：把模板对日志的既有要求扩展到窗口内的**所有**产物（日志、TSV、截图、`npm ci` / build 控制台输出、临时账套路径清单），并把两份证据分开：
    - **清理前的原始字节**：清理之前记录每个产物的路径、SHA-256、字节数与行数（二进制文件如 PNG 只记字节数与 SHA-256），保存为清单并入库或附到 PR；清单出来以前不清理；
    - **入库后的字节**：对入库文件按原样用 `git cat-file blob <提交>:<路径>` 取字节计算哈希，不用工作区检出的文件，也不要求统一为 LF（日志按模板有意保留 CRLF，PNG 是二进制）。两份哈希应一致；不一致时写明原因。

## 议题 2：`npm ci` 在窗口内运行（D493）

- **发生了什么**（观察）：Demo 模板第 17 条要求依赖安装在静默窗口开启前完成。DEMO-18 的两次 `npm ci` 都在窗口内运行。D489 只是把步骤 0 并入窗口，D492 只覆盖证据缺失，都不适用；协调者按 D493 一次性接受（窗口内没有其他负载，lockfile 精确安装，exit 0，前后 `status` 干净），不重跑。同一个窗口还出现了 D490（步骤 0 漏了必填参数 `-Shots`），说明窗口内的命令序列不是事先排练好的那一份。
- **根因**（推断）：第 17 条写在模板里，但开窗口的一方没有逐项核对；窗口开启时“依赖已装好”没有可见证据，于是安装顺延到窗口内。D489 把步骤 0 挪进窗口，也让“窗口前做什么、窗口内做什么”的边界变模糊。
- **改进**：
  - 行动 2：`npm ci` 必须在窗口开启前完成。版本管理在申请开窗口时附 `npm ci` 的退出码、lock blob 和随后的 `git status --porcelain`（应为空）；协调者看到这几项才开窗口。窗口内要执行的命令（含参数）按演练记录逐字列出，窗口内照单执行。

## 议题 3：RC 文档的数字、哈希与时序（三轮评审）

- **发生了什么**（观察）：#286 打回 3 轮，都是文档精度：
  - 计数：正文写“32 项检查”，实际是 23 项检查加 9 条取证记录；
  - 标识：`319778c`（被测运行器头）被写成当前 RC 头；
  - 哈希：`processes-real.tsv` 写的是工作区检出文件的哈希，不是入库 blob 的字节；
  - 时序：README 与清单对 `npm ci` 是在窗口前还是窗口内说法不一；PR 正文留着一句过时的“当前头不变”。
  - 同期 #281（版本管理文档）也打回 4 轮。S17 行动 2 的三条自查（范围固定、否定说法附检索、控制字符）都执行了，但它们不覆盖数字、哈希和时序。
- **根因**（推断）：这些数字是在 RC 文档的不同位置分别手写的。某一处更正后，其他位置不会跟着变；也没有一个从命令输出直接生成的“唯一来源”可以对照。
- **改进（协调者已采纳，D495）**：
  - 行动 3：RC 送审前加一步“数字自查”。CHANGELOG、发布说明、Demo README 与 PR 正文中出现的数字分两类：当前可由命令得出的计数、哈希与 SHA 角色，在最终 head 上实跑命令并附输出；历史测量与时点（窗口内耗时、开窗与清理时间、开发 PR 的字节数）引用其固定来源（入库日志的提交与路径、来源 PR 链接），在最终 head 上只核对引用一致，不重跑、不重算、不改写。具体：
    - 计数：用命令从入库的结果文件里统计（例如检查数与记录数分开数）；
    - 哈希：入库文件按原样用 `git cat-file blob <提交>:<路径>` 的字节计算，标明是哪个提交的哪个路径；清理前的原始哈希引用行动 1 的清单，不在清理后重算；
    - SHA：完整 SHA 与角色（RC head、被测运行器头、工具头）一一列出，文中只引用这张表；
    - 时序：一条按时间排序的事件表（安装、构建、干跑、开窗、真实运行、清理），README 与 PR 正文都引用它，不各写一份；
    - 历史测量与时点（窗口内的耗时、开窗与清理时间、开发 PR 的字节数）不能在最终 head 上重新得到：在最终 head 上核对的是“引用与固定来源一致”，每个数字引用它的原始来源（入库日志的提交与路径、来源 PR 的评论或正文链接），不改写；
    - 最终 head 的 SHA 与核对输出写在 PR 正文中（提交不能包含自己的 SHA），仓库内的文档不写“当前 head”。
  - 自 DEMO-19 起写入 RC 送审清单（S19 文档任务 DOC-19）。

## 议题 4：构建来源仍在评审时才补齐
