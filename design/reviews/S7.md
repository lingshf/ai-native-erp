## 3. 评审裁定接受的例外

以下 3 项都由评审在对应 PR 上明确接受，只适用于该 PR，不改变后续任务的预算或判定口径。

### 3.1 PG-05：UI-11e CSS 合计 gzip-9 +8 B（#159）

- 任务预算是“CSS 合计 gzip 减少或不变”。实际：入口 `index.css` −5 B，按需加载的 `TradeOrders` CSS +13 B，合计 +8 B。Vite gzip 列中，入口不变，`TradeOrders` +0.02 kB。
- 原因：新规则写进单独压缩的小 chunk，删除全局规则只让入口少几字节。已尝试的更小写法也未达标。
- 裁定：评审按 [UI-1 通用验收](../tasks/README.md#ui-1界面逐步改进) #9 接受，保留作用域更窄的类规则。详见 [UI-1.md §5.4](UI-1.md#54-ui-11e订单列表-cell-link-圆角与-stylescss-删除记录d-7-完成)。

### 3.2 TORD-05：`INDEXED BY trade_orders_party` 固定语句（#161）

- 账套不跑 `ANALYZE`。按 SQLite 的默认估计，带 `party` 时仍会选主键 `(company_id=? AND order_id>?)` 扫描，不满足验收 3 的计划断言。
- 处理：只在带 `party` 的那一条预写语句上写 `FROM trade_orders o INDEXED BY trade_orders_party`，属于任务决定 4 允许的“按语句固定”。不加全局 `ANALYZE`，也不改其他语句。
- 维护约束：SQLite 在 `INDEXED BY` 指定的索引不存在时直接报错，不会静默退化为全表扫描。所以以后删除或改名 `trade_orders_party` 时，必须同步修改这条语句。
- 同一 PR 的连带改动：TORD-03 的“未知参数 → 400”断言原来用 `party=V1` 作未知参数。TORD-05 起 `party` 是合法参数，改为 `status=open`，仍断言 400。评审认定这不属于 D11 所禁止的削弱。

### 3.3 TORD-05：像素差结论收窄（#161）

- 订单页 base / head 16 对配对图（中 / 英 × 红 / 绿 × 1440 / 390 × 教学关 / 开），因为新增了筛选栏和教学句，全图差异像素都不为 0。
- 用按行对齐的工具（`tool__aligned-diff.ts`）比较后：8 对残差为 0；另 8 对残差 2–38 px，都在圆角和折叠箭头的抗锯齿边缘，像素位置已逐个列出。
- 裁定：结论收窄为“除教学新增句与筛选栏两处预期变化外，下移内容与 base 逐字节相同，只有表中列出的抗锯齿例外”。不再使用“下移部分内容不变”这一整体说法。

经过（来源：[run-through.md](../../docs/demo/v0.7.0/run-through.md)）：

1. 预检连续 6 次为 0，`npm run build` 成功；`run-main.ps1` 完成迁移、启动和两条 seed。

根因与修复（D228）：

- 这是 Demo 脚本的缺陷，不是产品缺陷：服务端按规则拒绝了无收入科目的销售行。

- 修复：脚本先建服务类商品 SERVICE（收入科目 4000），销售单改用它。新增 `seed-orders-stub.mjs`，在假 HTTP 服务上按产品规则校验请求序列；它对旧脚本报错退出 1，即复现了中止原因。
- 修复后先做一次无浏览器的真实服务演练（4 张订单均 201），再申请第二个时段。
