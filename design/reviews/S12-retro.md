## 议题 1：时段内其他会话的本地 node 打断 L5

- **发生了什么**（观察）：
  - REFAC-01b 的 L5 在 14:50Z 中止，`processes.tsv` 记录的是 M2-05b 在本机运行的 vitest。
  - S12 内也有同类中止：TORD-06 D381 采到 worktree `lingshf-ideal-dollop` 的外部 vitest（counted=19）；Demo 第 2 次采到外部进程（counted=1）。
- **根因**：
  - 路线图 §5 的“批时段前收齐回执”（S11 行动 4）只停“vitest / biome / playwright / 浏览器 / 构建”。开发会话在自己的修订回合里仍会跑定向 vitest，并认为这算“验证交给 CI 之前的本地自测”，不在停用之列。
  - （推断）回执只说明发出时已停，不约束之后的回合。会话在时段中途收到新任务（M2-05b 正在修订），就会重新开跑。
- **改进**：D442 已定：时段内其他会话一律不在本机运行 node（含 vitest、tsc、biome、vite、npm）。只写文档、用 git / gh，直到协调者通知时段结束。本回顾把它写成行动 1。

## 议题 2：漏停自动重试循环，两次运行未经批准

- **发生了什么**（观察，#233 README §3）：版本管理为 D426 启动了一个自动重试循环，事后没有停掉。06:12 PT 循环自行启动一次（预检超时 exit 3），06:53 PT 再启动一次（exit 0，52 张）。两次都没有时段批准。D444 事后采纳了第二次的截图。
- **根因**：
  - 时段规则只规定“批准后跑”，没有规定“只能手动单次运行”。重试循环把“批准一次”变成了“批准之后的任意次”。
  - 会话结束前没有检查自己留下的后台 shell。
- **改进**：D444 已定：时段内只允许手动单次运行，不写自动重试；每次运行后、交回时段前，列出并结束自己留下的后台 shell。本回顾把它写成行动 2。

## 议题 3：截图脚本断言过严，DEMO-12 连续失败 4 次

- **发生了什么**（观察，[评审 §4](S12.md#4-demo233)）：第 1、3、4 次都因断言中止：
  - 第 1 次：徽标文本带图标字符 `!`；
  - 第 3 次：16 px 留白实测 0；
  - 第 4 次：正则把可访问名称里的 trade 当成原始模块键。
  三处都不是“截图拍错了”，而是脚本对文案、样式的判断写得过严或写错。每失败一次就要重新申请时段。
- **根因**：
  - S11 行动 5 要求“断言要有对照态”，防的是假阳性；但没有区分“截图前提”和“被演示内容的检查”，结果所有检查都带着失败判定。
  - 文案、间距这类检查在任务的 jsdom 测试与体积对照里已经验收过，Demo 再拿它们做失败判定，等于在最贵的环节重复验收。
- **改进**：D440 / D441 的原则：只有判断截图是否拍对的断言（参数、就绪、语言 / 主题 / 宽度 / 路由 hash、对话框与关键文本可见、列表与 API 集合一致）保留失败判定；其余只记录到 `checks`，由评审读记录值。本回顾把它写成行动 3，并写进 Demo 模板。

## 议题 4：开票列表“0 px 留白”——测量对象与任务书不一致

- **发生了什么**（观察）：Demo 实测筛选表单外框顶部与卡片标题底部间距 0 px，表单内边距 16 / 20 / 16 / 20 px；截图中标题下边线与“伙伴”标签之间有可见空白。
- **判定**：**不是缺陷，不进 S14 候选。**
  - TINV-08 要求的是“筛选栏与标题之间有留白”，是视觉要求，没有指定用外边距实现。表单内边距已经给出 16 px 的可见空白，满足要求。
  - Demo 脚本量的是外框间距（margin），与任务书要求的不是同一个对象。
- **根因**：
  - 任务书的视觉要求只写了“留白约 16 px”，没写从哪条边量到哪条边。
  - 取证脚本按自己的理解挑了一个对象，量出 0，又带着失败判定，于是有了第 3 次失败和一次设计口径确认。
- **改进**：S14 DEMO-14 已改为测量“卡片标题底部 → 首个字段标签顶部 ≥ 16 px”，只记录（[#234](https://github.com/lingshf/ai-native-erp/pull/234)）。本回顾把通用规则写成行动 4：任务书里凡是带数值的视觉要求，都写明测量对象的两端。

## 议题 5：S13 期间的设计例外

- **发生了什么**（观察）：
  - **D437**：M2-05a 评审中，为记录 J6 期初阶段耗时，在冲突域外的 `legacy-import.ts` 加了 3 个可选钩子（+7 行），只记录、行为不变（#227）。
  - **D439**：REFAC-03b 的 P7 路由预算原定 ±0；`CompanyJournals` 在 `_Journals` 共享块里，拆成只收 props 的组件后实测 +1288 B，放宽为五个路由同一口径 ≤ +1.5 KB，并另立 REFAC-04（方案 B）。
  - **D443**：M2-05b 需要新增测试文件，任务书未列，评审中批准。
  - S12 本身也有两次：REFAC-02 的 D401（入口 +32 B 上限）、SLOT-02 的 D411 / D412（改 `procs.ps1` 与规则 R1 → R2）。
- **根因**：
  - 任务书定预算时，没有先在实际 base 上对拆分方案做一次体积试算；“只搬移”的任务默认 ±0，而共享块的位置决定了它不可能是 ±0。
  - 冲突域按“要改的文件”列，没有列“为取证需要的观测点”和“可能新增的测试文件”。
  - （推断）这些例外都在评审中途、由协调者临时裁定。开发要等裁定，打回轮次因此增加。
- **改进**：行动 5：任务书在定数值预算前，先在实际 base 上试算一次并写出数字；冲突域一节单列“取证所需观测点 / 新增测试文件”，没有就写“无”。

## 议题 6：两个首发任务各打回 5–6 轮

- **发生了什么**（观察，[评审 §6](S12.md#6-过程数据)）：#208 打回 6 轮、#209 打回 5 轮，占 S12 打回总数的 38%。其中 #208 第 3、6 轮和 #209 第 3、5 轮没有新的静态问题，只是还没有时段证据或实际 base 的测量。
- **根因**：送审时没有说明证据是否齐全。评审只能给出 CHANGES_REQUESTED，于是“等证据”和“有缺陷”混在一起计数，也看不出哪一轮还需要开发改代码。
- **改进**：行动 6：PR 正文写明送审阶段，“静态评审（证据待补）”或“完整送审”；评审对静态评审可只给静态结论，不计作打回。是否这样计数由协调者决定。
