## 议题 1：`slot-run.ps1` 两次调用错误（D498、D499），步骤 0 又进了窗口（D496）

- **发生了什么**（观察，来源：[run-through §2](../../docs/demo/v0.18.0/run-through.md)）：
  - 4a：用 `powershell.exe -NoProfile -File` 调用，脚本在版本检查处退出（退出码 2，`slot-run.ps1 needs PowerShell 7 (pwsh)`），主体未运行。按 D498 改用 `pwsh` 重跑。
  - 4b：用 `pwsh`，但在 tool worktree 内调用。runner 以当前目录为 Root，找不到 app 里的 `run-main.ps1`，demo-capture ABORT（退出码 -196608）。失败前已完成预检（head / base 各 exit 0）、构建（写入 tool worktree 的 `dist`）与进程采样；没有起服务、造数或开端口。按 D499 改为在 app worktree 内调用 tool 的脚本，作最后一次。
  - 4c：`cd <app>` 后 `pwsh -NoProfile -File <tool>\scripts\slot\slot-run.ps1 -OutDir <新的空目录> -StepsFile <app>\docs\demo\v0.18.0\scripts\steps-demo19.ps1 -BaseRoot <tool> -Ports 4203`，exit 0。
  - 另外，D496 把步骤 0（`-SkipCapture`）作为第一步放进窗口，与 DEMO-18 的 D489 相同。
- **根因**（推断）：
  - S18 行动 2 要求“窗口内命令逐字取自演练记录”，但步骤 4 的 `slot-run` 会起服务、占端口，窗口前不能演练；它的调用方式（哪个 shell、在哪个目录、Root 取哪一侧）只存在于以往的经验里，没有写成逐字命令。
  - `slot-run.ps1` 用当前目录作 Root，又在预检、构建之后才发现 Root 下没有 `run-main.ps1`。4a 的版本检查是“先检查再动作”，4b 缺少同样的前置检查。
- **改进**：
  - 行动 1：开窗申请附**每一步**的逐字命令行（含 shell、当前目录、全部参数），步骤 4 直接取 run-through §2 那条 4c 命令，只替换版本路径、`-OutDir` 与 `-Ports`（填本次拟用、经协调者批准的端口，不沿用 D497 的 4203）；批准后窗口内执行的命令与申请逐字一致；协调者核对后开窗。步骤 0 是否在窗口内，在申请中写明并引用 D489 / D496，不在窗口内临时决定。
  - 行动 2（工具，S21 候选）：`slot-run.ps1` 在预检之前检查调用位置（Root 下存在 `-StepsFile` 所引用的脚本，或者 Root 与 `-BaseRoot` 不是同一 worktree），不满足就以非 0 退出、不做任何动作；与“`slot-run.ps1` 改用 `assert-web-dist.ps1`”合并为一个任务。`scripts/slot/` 由 `check-manifest` 管理，不在 DEMO 进行中改。

## 议题 2：临时账套路径没有记录（D500）

- **发生了什么**（观察）：#293 第 1 轮指出“临时账套路径清单”只有 3 次运行的汇总，没有实际目录。`run-main.ps1` 第 14 行用新 GUID 建 `erp-demo-<guid>`，第 39–41 行的 `finally` 在返回前删除它；脚本不输出这个路径，日志、slot 输出与 D492 的 CSV 里都没有原文。协调者按 D500 接受为缺口，不重跑。
- **根因**（推断）：D492 的清单要求“临时账套路径清单”，但没有说路径从哪里来。账套由脚本自己创建、自己删除，操作者看不到路径；清理前再去找，已经没有了。
- **改进**：
  - 行动 3：DEMO-20 的清理前产物清单列出每次 `run-main` 实际使用的账套完整路径（D500）。路径来源写进流程：`<版本>` 的 `run-main.ps1` 在创建账套后立即把完整路径写到输出（一行，例如 `demo book: <路径>`），由日志在 `finally` 删除之前留下原文；清单引用日志的路径与行号。改了 `run-main.ps1` 就按 D487 在窗口前的 `-SkipCapture` 演练中实际运行。

## 议题 3：RC 评审的取证缺口与证据格式

- **发生了什么**（观察）：#293 共 4 轮（3 次打回、1 次批准），三次打回都计入。评审确认产品、工具与 Demo 脚本从被测头到 RC 头都没有差异，17 项检查与 7 条记录、TLIST-03 键盘与 390 px 都吻合。打回点分两类：
- **取证缺口**（不是格式，改写法补不回来）：[首轮](https://github.com/lingshf/ai-native-erp/pull/293#pullrequestreview-6031338437)发现临时账套的实际路径从未留存（见议题 2）；协调者按 D500 接受为缺口、不重跑后，[复评](https://github.com/lingshf/ai-native-erp/pull/293#pullrequestreview-6031370221)才解除这一阻塞。对应行动 3。
- **证据格式**（首轮起各轮，对应行动 4）：
  - **如实写副作用**：4b 在 run-through、CHANGELOG Demo 段与 PR 正文被概括为“无副作用”，实际已做预检、构建与进程采样；第 2 轮仍有 CHANGELOG 与 PR 正文没有同步；
  - **固定 SHA**：`diff --check` 与 diff 自查以移动的 `origin/main` 为 base；D483 的两点 / 三点比较缺固定 SHA 与输出（第 1、2 轮）；
  - **完整哈希**：19 项的 SHA-256 只写了前 12 位（第 3 轮）；
  - 另有计数与归因：干跑截图 CSV 中 6 张、文档写 5 张；JSON 字节一致被归因于 `.gitattributes` 的 `-text`（只匹配 `*.log`），实为哈希实测结果。
- **根因**（推断）：取证缺口的根因见议题 2（路径由脚本自建自删，清单没有规定来源）。格式问题：D495 的自查落在了 RC **文档**上（唯一的两张表做到了），但 PR 正文的证据块仍是手工摘录：为了可读截短哈希、沿用平时的 `origin/main` 写法、把失败步骤压缩成一句结论。同一事实在 run-through、CHANGELOG 与 PR 正文各写一遍，改一处漏一处。
- **改进**：
  - 行动 4：D495 的自查扩展到 PR 正文证据块，四条格式规则：
    - **完整哈希**：SHA-256 与 Git OID 一律写完整值，不截断（行文中可简写，但证据块与表格必须完整）；
    - **固定 SHA**：证据命令里的 base / head 一律是完整 SHA，不出现 `origin/main`、`main`、`HEAD`；D483 的两点 / 三点比较附固定 SHA 的命令与输出；
    - **如实写副作用**：每个失败或中止的步骤，按它的日志列出实际执行过的动作（预检、构建、采样、写入的路径、是否起服务 / 造数 / 开端口），不写“无副作用”这类结论；同一事实只写在 run-through，CHANGELOG 与 PR 正文引用它；
    - **计数与归因来自命令**：计数从入库结果或清单统计并附命令；“某项一致”的理由写实测方法（哈希比对），不推断为某条配置的保证。
  - 协调者送审前按这四条核对；落点见下文汇总。
