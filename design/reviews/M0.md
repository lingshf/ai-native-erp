## 3. 架构与设计原则（SOLID，不过度设计）

- 与 [M0 架构](../m0-architecture.md) 一致：3 个包，分层由脚本检查；TS 源码直跑；纯 Fastify；没有 PG；开启 WAL；一个总账模型。worker 执行器是唯一的执行方案（`infra/src/main.ts:13-20`），没有“同步/异步两套并存”。
- 没有发现只有一个实现的抽象层，也没有未使用的扩展点。本地 `packages/{application,domain,ui,contracts,infrastructure}/dist` 是被 git 忽略的旧构建残留，不在仓库里。
- **发现 1（影响 M1）**：控制科目（AP/AR 等）现在只能被拒绝，没有正向过账路径。手工凭证在 `core/src/domain/journals.ts:250` 拒绝；业务事件在 `core/src/application/business-events.ts:301` 只接受 `general` 科目。旧的 Enterprise 账里的单据日期/税日期也没有迁移。M1-03 发票需要“已登记的业务适配器才能过账到控制科目”（FR-C02/FR-T03）和“税率按 taxDate 取”（FR-T02），而 M1-03 的任务文档没有写这两点 → 新建 **M0-R1**，阻塞 M1-03。
- 科目和维度列表按 100 条游标分页加载（`fetchNextPage`，见 `web/src/Accounts.tsx:121-131,175`、`web/src/Dimensions.tsx:107-117,282`），超过 100 行时虚拟滚动，符合要求。M1 的伙伴/商品/单据列表沿用同一做法。

Bench 慢的原因：`.github/workflows/bench.yml` 写死了基线 `5b23d8c`。每次都要再检出一份旧代码、装一次依赖，跑完基线再跑候选，并扫描 R=2/3/4。手动运行中有一部分超过 20 分钟；定时运行还没有实测。如果每晚都按约 20 分钟运行，Bench 一个月约 600 分钟，占 1200 分钟目标的一半 → **M0-R3**。

### 重复 / 低价值 / 缺失

- 重复：报表合计在 application 层和同一文件的 HTTP 契约用例里都断言了一遍（`infra/test/application/reports.test.ts:88` 与 `:314`）→ HTTP 层只测契约和状态码。旧账的输入拒绝在 `legacy-teaching:29`、`legacy-cli:128`、`legacy-http:181` 各测一遍 → 规则只在最低层测，CLI/HTTP 各留一个代表用例。凭证幂等在 application:109 和 web journals:237 都有，但属于不同层，可以保留。
- 低价值：`core/test/application/runtime.test.ts:5` 只测纯委托 → 删除。`infra/test/tooling/ci.test.ts` 检查 CI 接线，作为防回归可以保留，但不要再加。`web/test/ui.test.ts` 检查中英文标签是否成对，属于资源完整性检查，保留。
- 缺失：D8 的 409 和 M0-13a 的专用槽位、写 worker 丢失后返回 503 再恢复都已有测试（`workers.test.ts:55,103`），没有发现必须补的缺口。Windows 上 `INVALID_SNAPSHOT` 间歇失败还没有复现用例 → **M0-R4**。

- lockfile 里只有公共 registry 地址，防回归检查在 PR CI 中生效，Dependabot npm 更新已恢复（#10 vite、#11 copilot-sdk、#16 react 组都能正常生成且 CI 绿）。
