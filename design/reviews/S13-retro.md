## 议题 1：TORD-07 合并后 main Full 红了 35 分钟

- **发生了什么**（观察）：
  - #223（TORD-07）在 09:11Z 合并，合并提交的 Full 在 `trade-gui-zh-red-2` / `trade-gui-en-green-2` 两个浏览器分片失败。原因是 e2e 的 `orderInvoicingFilter` 仍断言“筛选后地址不变”，而 TORD-07 正是把筛选写进地址。
  - 之后 #225、#228（设计文档）和 #226（REFAC-03 产品代码）继续在红的 main 上合并，Full 同样失败。
  - 09:46Z hotfix #229（D436）只改这条断言（+3 / −3），`8f660a6` 的 Full 转绿。
- **根因**：
  - **任务书列举不全**：TORD-07 的 K8 列出了 tests:trade-e2e 中必须继续成立的三处订单页断言（`:276–280`、`:332–340`、`:876–883`），漏了会因新行为而失效的 `orderInvoicingFilter`。任务书只问了“哪些断言不能坏”，没有问“哪些断言会因为本任务而必须改”。
  - **冲突域不允许改**：tests:trade-e2e 由 REFAC-01b 独占，TORD-07 即使发现了也不能改，修复没有预先指定归属。
  - **合并前看不到**：PR CI 排除 `*.slow.test.ts`，`full.yml` 没有 `workflow_dispatch`，浏览器分片只在合并后运行（#229 正文）。
  - （推断）main 变红后没有暂停合并的规则，所以又有 3 个 PR 合了进去，其中一个是产品代码。
- **改进**：
  - 行动 1：改变页面地址、文案或交互的任务，任务书用路由名、标签键搜索 tests:trade-e2e，列出两类断言：“必须继续成立”和“须随本任务改”。后者写明由谁、在哪个 PR 里改；若落在别的任务的独占冲突域，写明交接方式。
  - 行动 2：main Full 失败期间，只合并修复它的 PR 与只改 `design/` / `docs/` 的 PR，直到转绿。
  - Full 能否在 PR 分支上手动触发，作为候选另议（成本是 Actions 分钟数）。

## 议题 2：夹具的类型错误到时段才暴露

- **发生了什么**（观察）：M2-05b 新增的 `legacy-opening-fixture.ts` 第 114、118 行有 2 个 tsc 错误（TS2339、TS2345），PR CI 与 Full 都是绿的。DEMO-13 时段第一步的 SLOT-02 预检发现了它，exit 6 中止；D449 决定跳过这一项后才继续。S14 FIX-01（#241）修复。
- **根因**（[FIX-01 任务书](../tasks/S14.md#ci-的-typecheck-为什么没有拦住)已查明）：
  - 根 `tsconfig.json` 只收录 infra 测试目录下的 `tooling/ci.test.ts`，`npm run typecheck` 从不检查 `test/support/**`。
  - vitest 只转译、不做类型检查。
  - 唯一覆盖这些文件的 `tsconfig.preflight.json` 只在时段 runner 里运行。所以 DEMO-13 的时段是这个文件第一次被类型检查。
- **改进**：行动 3：把 SLOT-02 预检的 tsc 部分放进 PR CI，基线外出现新错误键即失败（S14 候选池，排入 S15）。完成后，时段预检只剩下兜底的作用。

## 议题 3：任务书的证明条款送审前没有试跑

- **发生了什么**（观察）：设计打回 8 次，占全部打回的 47%（S12 为 7 / 29）。打回点多数不是范围或取舍问题，而是证明或测量条款在 base 上执行不了：
  - #225：要求用 `TypeChecker.getExportsOfModule`，但仓库是原生 TypeScript 7，没有可供脚本调用的 Compiler API（→ D433 改用 Babel）。
  - #230 第 2 轮：P4a 要求 A 未返回时点击 B，base 中 B 按钮已禁用、`working` 锁拒绝重入，B 根本不会发请求。
  - #230 第 3 轮：P4a-2 的 `alive` 清除从页面结果判定不了。
  - #222：L2 的 base / head 取样范围不对称，原样保留的模块层字符串会被算成新增。
  - #228：N4 要求第 2 批前失败时“GL 批次全部保留”，与现有事务边界矛盾。
- **根因**：
  - 写验收时只推演了代码，没有在实际 base 上把每条证明“走一遍”：工具是否装了、路径能否触发、两侧能否在同一点取样。
  - （推断）S12 行动 5 只要求对数值预算先试算，没有覆盖证明类条款。
- **改进**：行动 4：任务书送审前，对每条证明或测量条款在实际 base 上做一次可行性核对（工具可用、路径可达、两侧可同点取样、判定能区分对与错）。在 PR 正文列出核对结果；做不到的条款改写或删掉，不留给评审发现。

## 议题 4：Demo 脚本在时段内才发现错误

- **发生了什么**（观察）：
  - DEMO-13 第 2 次运行因就绪检查写死不存在的公司 `DEMO2` 而失败，发生在拍任何截图之前。README 自述“未做：`slot-run -Stub` 桩演练”。
  - #236 又打回 2 轮，都关于归档脚本的可复现性：归档目录下缺依赖，无法运行；复现命令指向的提交里是旧脚本。
  - #235 打回 1 轮，原因是证据链接没有固定到 gist 修订。
- **根因**：
  - 就绪检查的公司名和发票号是手写的，没有从 seed 夹具派生，也没有在时段外对着同一 seed 跑过。
  - D446 只允许把脚本放进 Demo 目录，没有规定归档脚本要么能在原地运行，要么标为审计副本并写清复现步骤。
  - S11 行动 6（正文与运行记录一致）的检查清单没有覆盖“链接固定修订”和“复现命令能跑通”。
- **改进**：行动 5（版本管理）：
  - 申请时段前，用 `slot-run -Stub` 对同一 seed 跑一遍桩演练；就绪检查的数据从 seed 派生。
  - 归档脚本或能原地运行，或标为审计副本并写清复现步骤。
  - 发布清单加两项：所有证据链接固定到修订；复现命令在归档提交上核对过。

## 议题 5：只缺证据的打回仍在出现

- **发生了什么**（观察）：#224 第 1 轮（静态评审，L5 待补）和 #226 第 1 轮都只要求补附脚本与未截断输出，评审明确“无需改代码”。两个 PR 的正文都只写了 `PASS` 和计数。
- **根因**：完成定义要求“附证据”，但没有说明证明类验收的证据最少包括什么。开发按“结论 + 计数”理解，评审按“可独立复核”理解。
- **改进**：
  - D451 已把这类轮次改记为“待证据”（自 S14 起），解决的是计数问题。
  - 行动 6 解决来源：路线图 §5 完成定义写明，证明或测量类验收须在 PR 正文附上脚本原文与未截断输出，或链接到固定修订；只写结论和计数不算附证据。
