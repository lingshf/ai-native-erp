## 议题 1：RC / Demo 返工 5 轮，证据与日志没有按可核验的方式保存

- **发生了什么**（观察，轮次见[评审 §6](S10.md#6-过程数据)）：
  - **证据清单不全**：#191 两轮都在补证据：第 1 轮缺证据索引；第 2 轮缺 PROC-05 逐项结果（含从渲染后的 `<pre>` 复制执行）、实际核对时间、head 与 verify 链接，以及 #188 slot-5 的 gist 链接。第 1 轮还有 4 处发布说明口径问题：把 GATE-01 −82 B 与 TINV-05 +382 B 合成“入口块更小”；提到按计划不进发布说明的 CSS-02 并称其“冗余”；390 布局描述错误；写了不存在的“先迁移到 017”。
  - **日志被删**：D332 取图成功后，按 README 取图块的写法清理了临时目录；完整日志只在本机临时目录，检查后被删（`docs/demo/v0.10.0/run-through.md:59`、`:61`）。
  - **`*.log` 被忽略**：D333 的日志写进了 `docs/demo/v0.10.0/logs/`，但 `.gitignore:9` 的 `*.log` 让它没有进提交；第 3 轮打回后用 `git add -f` 并加 `logs/.gitattributes`。
  - **`Copy-Item` 的非终止失败**：取图块按 `docs/demo/TEMPLATE.md:92–93` 把 `$ErrorActionPreference` 设为 `Continue`，以便原生命令的 stderr 落盘。但同一块里的 `Copy-Item` 也因此不再抛出终止错误，复制失败会绕过 `catch`，块仍记成 `exit=0`，随后删除源截图。D333 前加 `-ErrorAction Stop` 修复，并补了“复制失败保留原图”的替身回归（`run-through.md:77`）。
  - **导航路径**：#192 第 1 轮，订单详情截图来自 `page.goto` 直接打开，没有证明“点击发票列表的来源链接后到达”；D332 改为真实点击后重取。
- **根因**：
  - 模板只规定了**失败**时保留现场（`docs/demo/TEMPLATE.md:110`），对成功路径没有要求“先记录日志的哈希与行数、日志永不删除”；日志默认放在 `$env:TEMP`（`:88`），本来就不入库。入库路径是否被 `.gitignore` 忽略，没有任何一步会检查。
  - 为原生命令设的 `Continue` 作用于整个块，模板没有提醒块内的 cmdlet 要单独加 `-ErrorAction Stop`；PROC-05 固定负例组没有“非终止错误”这一类，替身因此没有覆盖到。
  - RC 正文没有固定的证据索引格式，每次靠评审逐项追问。发布说明没有对照计划里“不进发布说明”的清单（[S10 不合并结案 2、6](../tasks/S10.md#不合并结案与门禁解锁)）逐项核对。
  - **设计侧**：DEMO-10 验收 2 只写了“点该链接后到达订单页 `?order=` 打开的销售订单详情”，没有要求截图必须由这次点击产生、且与断言来自同一页面实例，`page.goto` 因此看起来也满足字面要求。
- **改进**：见行动项 1–4。

## 议题 2：1440 / 390 断言的适用范围（slot-2 中止）

- **发生了什么**（观察）：
  - TINV-05 任务书 `design/tasks/TINV-05-invoice-list-filters.md:139` 写的是“1440 / 390 下‘来源订单’列宽与行高不因筛选栏改变（沿用 `sourceOrders()` 中的列宽断言，`:1361–1397`，不改其期望值）”。
  - 实际上 `sourceOrders()` 在 1440 下只截图，切到 390 后才测 `row: 44` 与 `cell <= 240`（[评审 6011238355](https://github.com/lingshf/ai-native-erp/pull/189#pullrequestreview-6011238355) 第 2 点）。#189 正文照搬了任务书的说法，被第 1 轮打回。
  - 补 1440 断言时，开发者把 390 专用的阈值 240 用到了 1440：D322（slot-2）中止，`expected 261 to be less than or equal to 240`（`trade-gui-scenario.ts:1388`，zh-红 1440；en 为 205.66，恰好通过）。D323 定下口径：240 只适用于 390；1440 下断言筛选前后列宽相等、base / head 几何一致。slot-3 通过。
- **根因（设计侧）**：
  - 任务书对**现有测试**做了一条肯定性断言（“沿用……中的列宽断言”），没有核对这条断言在哪个视口下执行。S9 回顾行动 7 只要求否定性断言附出处，肯定性断言没有覆盖。
  - 任务书把两个视口写在同一句里，没有分别写出每个视口要测什么、阈值是多少、来源在哪一行。阈值只在 390 下有设计依据（26ch 列宽，D287），1440 下应该比较前后是否相等，而不是套用固定上限。
  - 推断：如果任务书按视口逐行列出“测量 × 阈值 × 来源行”，slot-2 的误用和第 1 轮打回的第 2 点都可以避免。
- **改进**：见行动项 5、6。

## 议题 3：独占时段进程采样规则（D311–D320）

- **发生了什么**（观察，#188 正文“D312 作废与采样器修正”节）：
  - D310 中止后，开发者按 D311 改了采样器：先按命令行模式预筛候选，再判归属。D312（slot-3）在该规则下 exit 0。
  - 评审用原谓词复现：本仓库的 `vite build`、非 headless 的 `chrome.exe` 与读不到命令行的进程在归属检查之前就被跳过（[6011104634](https://github.com/lingshf/ai-native-erp/pull/188#pullrequestreview-6011104634)）。D312 作废。
  - 修正分三步：D314 候选只按进程名判定，读不到命令行的计为“归属不明”；整机试算有 20 个归属不明的进程（用户自己的 Edge、Ollama 等），预检无法通过，于是有 D315 系统浏览器排除（(a)–(d) 四条同时满足）与 D316 孤儿 cmd 规则（cwd 可读且无仓库证据、至少 1 个子进程、子进程都是系统位置的非候选程序）。自测从 13 项增至 27 项。
  - 第 2 轮评审发现代码里还有一条 PR 正文没写的 `cmd.exe` 排除分支：父进程是仍存活的系统位置 launcher（`procs.ps1:171–172`），不要求 cwd 可读、不看子进程（[6011176393](https://github.com/lingshf/ai-native-erp/pull/188#pullrequestreview-6011176393)）。D320 追认它为 D315 的一部分；评审逐笔核对 slot-5 的 780 条排除记录，没有命中该分支，证据接受。
  - 采样器与自测只在私有 gist（379 个文件），不在仓库里。
- **根因**：
  - 规则散在决定编号（D311、D314–D316、D320）和 PR 正文里，没有一处列出“当前有效的全部排除规则”。评审只能拿代码和正文逐条对照，正文漏写的分支要靠读代码才能发现。
  - 排除分支没有“每条分支都必须有规则编号、且有正反自测”的约束。日志里虽然写了命中的规则，但没有反过来检查“代码里的每个排除出口都在规则清单里”。
  - 推断：规则一放宽就会漏计（D315 的“同机普通 Edge 跑负载会漏计”、launcher 分支的“系统位置程序拉起 cmd 跑负载会漏计”）。这些代价只写在 PR 正文里，下一个申请时段的开发者看不到。
- **改进**：见行动项 7、8。

## 议题 4：GATE-01 的 3 次中止各有原因，未形成通用改进

- **观察**：D308 场景脚本 TDZ（`draftPrefix` 在声明前被引用）；D310 外部仓库的 `tsc`；D317 base 截图 20 px 渲染抖动（D318 维持 0 px 标准）。D308 之后开发者补了无浏览器自查（同块 TDZ 检查、`page.evaluate` 回调在 vm 中实际运行），此后没有再因脚本错误中止。
- **判断**：D310 属于收齐“已停”回执之后仍出现的外部进程，按现行规则立即中止、不在原时段重跑，处理正确；D317 是渲染抖动，0 px 标准不放宽是对的。D308 的无浏览器自查值得推广，但它是 GATE-01 场景专用的检查，S11 先观察是否复发，不单列行动项。
