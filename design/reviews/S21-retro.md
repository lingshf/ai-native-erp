## 议题 1：第一窗口失败在 capture 新脚本的焦点路径

- **发生了什么**（观察，run-through“第一窗口”）：
  - 第一窗口 18:36:10 PST 开窗，步骤 1（干跑）退出码 1：拍完 8 张截图后，在“草稿编辑器打开时 Tab 应能到达 Refresh list”一步失败（`capture-dry-run.out-w1.log:41`）。步骤 2 未跑。
  - 原因是 DEMO-21 新写的 `capture.mjs`：先 `blur()` 再按 Tab，焦点起点落在编辑器位置，越过了按钮。不是产品缺陷。修正为“聚焦按钮之前最近的可聚焦元素，再按一次 Tab”，并记录起点（实测 `a:Trial balance`）。
  - 修正后申请第二窗口，18:40:42–18:43:51 PST 通过。整个 Sprint 因此多用了一次窗口，REFAC-12 等开发工作再暂停一次。
- **根因**（推断）：
  - `-SkipCapture` 正好跳过 capture，所以开窗前的实跑证明不了 capture 脚本；S21 计划把“新增或改动的 capture 脚本在窗口内干跑”作为唯一门禁（D487），新的键盘步骤第一次执行就在窗口内。
  - 焦点起点用 `blur()` 这种“不确定起点”的写法，在任何环境下都无法预先知道 Tab 会落到哪里；这一点从 DOM 顺序与组件测试就能看出来，不需要浏览器。
- **改进**：行动 2。

- **发生了什么**（观察）：#310 共 3 轮（2 次打回、1 次批准），比 #302 少一轮。评审确认 Demo 脚本、日志与截图在评审期间没有改，各轮都写明不重开窗口、不重测。

- **证据格式与可更正的表述**：
  - **事实表述**（第 1 轮）：把第一窗口的队列键盘场景写成通过（`capture.mjs` 中它排在失败断言之后，没有执行）；批准原文没有逐字给出（写成 `Add-Content …`）；把 D512 正项（#304 的 4c Stub 批准）写成开窗授权本身。

  - **同一事实只写一处**（第 1 轮）：两窗结果与 `--hash` 失败在 PR 正文、Demo README 中重复；Demo README 的 ancestry 表缺 DOC-21。

- **根因**（推断）：这些都已在送审清单中有对应条款（DOC-21 #305 的四条、DOC-22(a) #309 的 `git grep` 自查），属于执行偏差，不是缺规则。共同点是“手写转述代替原样输出”：转述 `git grep` 的命中、转述复原方法、转述步骤结论，转述时出错。DOC-22(a) 在 RC 范围终点 `a1a1244` 才合并，RC 是第一次按它执行。
- **改进**：不新增行动，继续按送审清单执行；DEMO-22 的送审自查须对 (3)、(4) 两条附原样输出（见行动汇总下的说明）。

## 议题 4：回顾行动写进模板时新增了未实测的技术断言

- **发生了什么**（观察）：#307 把 S20 回顾行动 1–4 写进 Demo 模板与送审清单，3 次打回：
  - 第 1 轮：第 25 条把 `-SkipCapture` 门禁限于改动过的 `run-main.ps1`（行动 4 要求每次 Demo 都实跑）；第 23 条要求记录 cwd，给的却是取不到 cwd 的 `Win32_Process` 命令；第 24 条写成 PowerShell 通则“加管道则退出码是管道的”，评审实测 `pwsh` 子进程退出 7、接 `Tee-Object` 后立即读 `$LASTEXITCODE` 仍是 7。
  - 第 2 轮：退出码只要求抄进 run-through，没有要求写进原始日志；“端口无监听”被读成窗口内也适用。
  - 第 3 轮：追加退出码的 `Add-Content` 没有要求列入获批命令原文。
- **设计侧的来源**（观察）：第 24 条的错误通则来自 [S20 回顾议题 2](S20-retro.md#议题-2窗口内的记录不足以归属进程也没有留下-runner-退出码d507d508) 的一句“当时看到的 ‘exit 0’ 是管道的退出码”。那是没有实测的推断，却写在“发生了什么（观察）”下。本 PR 按 S20 回顾行动 7（替换旧句，不追加更正）把它改为“无法确认是 runner 的退出码”。
- **根因**（推断）：回顾行动是一句话的要求，写成模板条款时要补“怎么做”，补的部分（命令、退出码行为、端口规则的适用时段）没有逐条实测，也没有逐条对照回顾行动的完成标准；评审一轮只能发现一部分，于是逐轮收敛。
- **改进**：行动 3。

## 议题 6：第二窗口的快照没有父进程链

- **发生了什么**（观察，tag 指向的 `90c762f`）：第一窗口的 [`gate-snapshots-w1.tsv`](https://github.com/lingshf/ai-native-erp/blob/90c762f05de39723852d1a381058301cab4da997/docs/demo/v0.20.0/logs/gate-snapshots-w1.tsv) 共 24 行（开窗前 18、窗内 6），其中 12 行有 `chain=…`（开窗前、窗内各 6 行），开窗前另有 12 行为 `chain=` 空值。第二窗口的 [`gate-snapshots.tsv`](https://github.com/lingshf/ai-native-erp/blob/90c762f05de39723852d1a381058301cab4da997/docs/demo/v0.20.0/logs/gate-snapshots.tsv) 有表头 `phase / time / pid / ppid_chain / cpu_s / cwd / cmd`，共 66 行（`pre` 18、`win` 48），`ppid_chain` **全部为空**。run-through 第 19 行列出了“父进程链”这一列，但没有写明值为空。核对命令：`git show 90c762f:docs/demo/v0.20.0/logs/gate-snapshots.tsv`，按列统计 `ppid_chain` 的非空行数为 0。
- **影响**：第二窗口是正式运行的窗口。窗内的 node 进程只能按命令行前 140 字符判断，不能归属到父进程链，S20 回顾行动 2 在这一窗口没有达成。没有因此出现误判或冲突，但这一点无法从快照证明。
- **根因**（推断）：快照是手工命令（#307 第 23 条），两窗用的写法不同（列格式不一致），第二窗口的链字段没有求值；开窗申请和门禁核对只查“有这一列”，没有查“值非空”。我写 S21 回顾初稿时也犯了同样的错，把“有字段”写成了“有链”（#314 评审指出）。
- **改进**：不新增行动，由 S22 的 SLOT-05（[#312](https://github.com/lingshf/ai-native-erp/pull/312)）解决：工具逐级写出父进程链（每级一行，带 `depth`），读不到的值写 `unreadable`、不写空串，并在 `note` 中写明停止原因（[SLOT-05 任务书](../tasks/SLOT-05-gate-snapshot.md)“设计决定”第 4、5 条）。DEMO-22 的门禁用这个工具，不再手工拼命令。S22 回顾检查 S20 行动 2 时，按“窗内每个 node 进程都有非空的链，或有 `note`”逐窗统计，不以列名存在作为证据。
