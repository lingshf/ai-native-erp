## 议题 1：数字与证据仍在评审时补

- **发生了什么**（观察）：
  - #262（TORD-08）唯一的一轮打回有 3 点，其中 2 点是证据：K4 的脚本与原始输出、构建来源的 Node / npm / OS 与 lock blob。
  - #263（S15 评审与回顾）打回 3 轮。第 1 轮是三次时段失败记录不全、SR-C3 归因未经日志证实与 D469 措辞；第 2、3 轮是设计文字本身：v0.14.0 tag 的拓扑（D473）与祖先检查的精确退出码。
  - #266（SLOT-03）打回 2 轮，都是端口查询失败的处理：任务书只写了“端口空闲”与“端口被占用（exit 7）”，没写“查不了”算什么；第 1 轮（[6027987132](https://github.com/lingshf/ai-native-erp/pull/266#pullrequestreview-6027987132)）发现查询出错时被当作空闲，第 2 轮（[6028099950](https://github.com/lingshf/ai-native-erp/pull/266#pullrequestreview-6028099950)）要求保留全部错误记录。结论定为 exit 8、不重试（D475）。
  - 同一 PR 还需要越出冲突域改一行（D474，评审裁定接受，不是打回）：#263 在路线图 §3 加了一行含“进程采样规则 R3”的文字，`check-manifest.mjs` 按“进程采样规则”找第一处匹配，因此读错了位置。
- **根因**：
  - S15 行动 1（数字出现即附证据）直到 S17 的 #267 才写进路线图 §5（`roadmap.md:96`），#262 送审时还没有这条规则。
  - 设计文字被脚本当作输入（路线图 §5 规则表由 `check-manifest.mjs` 解析），但设计 PR 的自查不包括运行这个脚本；该脚本也不在 CI 中（`git grep -n check-manifest -- .github` 无结果）。
  - 门禁类条款只写了“通过”与“失败”，没有写“无法判定”。
- **改进**：
  - 行动 6：凡改动 `design/` 的设计 PR（不只改 §5 的；D474 的触发点在 §3），推送前跑 `node scripts/slot/check-manifest.mjs` 并附输出；门禁类验收（端口、预检、祖先检查等）必须写出第三种结果“无法判定”及其退出码或处理。
  - S15 行动 1 已在 S17 写入，S17 回顾再核对，不另立行动。

## 议题 3：干跑在新 worktree 缺 dist

- **发生了什么**（观察）：DEMO-16 第一次干跑（应用 `c7dd7cc`）exit 1，`not ready`。原因是新建的应用 worktree 没有 `packages\web\dist`，而 `run-main.ps1` 不构建（`docs/demo/v0.15.0/README.md:42–43`）。改为先跑一次 `npm run build`，再干跑通过（D481）。
- **根因**：D473 起，应用与工具分在两个 worktree，应用 worktree 每个时段都是新建的。以前在同一个开发 worktree 中演练，dist 总是现成的，这一前提从未写下。
- **改进**：
  - 行动 2：Demo 模板的干跑步骤第一条写明“在应用 worktree 跑 `npm run build`”。另建候选代码任务（不在本 PR）：`run-main.ps1` 启动前检查 dist，缺失时给出明确提示后退出，不再等到就绪超时。

## 议题 4：繁忙机器上 Web 全量测试超时

- **发生了什么**（观察）：
  - #262 正文：本地全量 vitest `Test Files 18 failed | 68 passed (86)`，失败都是超时 / BUSY；对 16 个失败文件用 `--maxWorkers=2` 重跑，`16 passed`，`292 passed | 1 skipped`。
  - #271 正文：Web jsdom 全量在负载下有数个未改动文件超时，每次失败的文件不同，单独运行都通过；开发以 PR CI 为准。
- **根因**（推断）：同一台机器上多个项目、多个 worktree 并行运行 node，jsdom 用例的默认超时与 worker 数按空闲机器设定。路线图 §4 只规定“耗时阈值以 Linux main Full 为准”，没有规定本地验证在繁忙机器上怎么做、算不算数。
- **改进**：
  - 行动 3：路线图 §4 增加“繁忙机器上的本地验证”：本地先跑受影响的测试文件；全量用 `--maxWorkers=2`；超时只重跑失败的文件，两次输出都附上；门禁以 PR CI 为准。不得为此调大测试超时或跳过用例（D11）。

## 议题 5：静默窗口成了每次时段的固定成本

- **发生了什么**（观察）：两次真实时段都在全会话静默窗口内完成（D478、D480）。预检都是前 6 次采样即为 0，SR-X6 分别记了 4 行与 2 行，都是“命令行不可读”。
- **根因**：
  - R3 只把归属不明的进程改为不计数；其他 ai-native-erp worktree 的进程仍按 D442 计数（SR-C2），多会话并行开发时只能靠人停下。
  - S15 行动 5 的完成标准写了“日志中每个 SR-X6 进程都有命令行”。采样器在无权读取时只能记“不可读”，这条标准按字面无法达成。
- **改进**：
  - 行动 4：把 D480 定为标准时段流程，写入路线图 §5：静默窗口 → 干跑 → `run-main.ps1 -SkipCapture` → 真实 `slot-run`，各一次，不重试，任何失败即停。S15 行动 5 的完成标准改为“SR-X6 每行有 PID、进程名与不可读原因”。

## 议题 6：CHANGELOG `[Unreleased]` 没有随合并更新

- **发生了什么**（观察）：S17 的 TLIST-01（[#271](https://github.com/lingshf/ai-native-erp/pull/271)，用户可见）与 REFAC-08（[#270](https://github.com/lingshf/ai-native-erp/pull/270)）已合并到 main，但 main 的 `[Unreleased]` 仍是“（暂无）”。由协调者在发布后指出。
- **根因**：CHANGELOG 只在 RC 时由版本管理集中整理，合并时没有检查；v0.15.0 打在 release 分支上（D482），main 上的条目更容易被遗漏。
- **改进**：
  - 行动 5：RC 送审清单加一条对照：`git log --oneline --first-parent <上一个 tag>..main` 中的每个 PR（本仓库 squash 合并，每行一个 PR），要么有 CHANGELOG 条目，要么注明“无用户可见变化”。DEMO-17 的 RC 写入 #271 与 #270 两条，#269（已随 v0.15.0 发布）与 #272（只改日期）单列为不需要条目（[S17 DEMO-17 验收](../tasks/S17.md#demo-17-验收)）。
