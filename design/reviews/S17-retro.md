## 议题 1：时段前演练没有执行新的取图脚本（D486）

- **发生了什么**（观察）：TEMPLATE 第 12 条要求申请时段前对真实服务做一次无浏览器演练，并覆盖 capture。DEMO-17 申请时只附了 `2b696ce` 上的 `slot-run -Stub`，而 `-Stub` 不运行 `run-main.ps1` 和 `capture.mjs`（TEMPLATE 第 16 条）。时段照常批准。真实运行 22/22 通过，协调者按 D486 不重跑（#277 `run-through.md` §6）。
- **根因**：
  - 路线图 §5“时段申请附演练记录”（D460）写的是“附 `slot-run -Stub` 桩演练（及无浏览器演练）”，括号里的那项读起来是可选的；协调者批准时段时只能看到 `-Stub` 记录。
  - 每个版本的 `capture.mjs` 都是新写的，而在真实 Chrome 之前唯一能执行它的就是无浏览器演练。这一步缺失时，新脚本第一次执行就是在真实时段里。
- **改进**：
  - 行动 1：路线图 §5 把“无浏览器演练”从括号里提出来，作为批准时段的必备条件：演练记录必须列出本版新增或改动的每个 Demo 脚本（`run-main.ps1`、`capture.mjs` 等），及其 blob、命令、退出码与输出摘要；缺任何一个，协调者不批时段。`-Stub` 记录只证明 runner 编排，不能替代这一项。

## 议题 2：RC 文档精度，三轮评审

- **发生了什么**（观察）：#277 评审了 3 轮（2 次打回，1 次批准），打回点都是文档，不是产品或证据：
  - 过时或错误的说法：把窗口内的取图干跑写成满足了 TEMPLATE 第 12 条；写“#275 没有体积测量”，实际 #275 R7 有 +757 B。
  - 范围没有固定终点：`git log --first-parent v0.15.0..main`。RC 撰写期间 #276 合并，`..main` 从 7 行变成 8 行；第 1 轮后正文改了，但 CHANGELOG 与发布说明里的命令仍是 `..main`。
  - 笔误：CHANGELOG 中 `trade-adjustments.test.tsx` 的首字母 `t` 被制表符替换（推断：转义序列 `\t` 被解释了）。
- **根因**：
  - “没有 X”这类否定说法是凭记忆写的，没有回到来源 PR 检索。
  - RC 撰写时 main 仍在前进，送审清单没有要求“发布文档中的范围一律用固定 SHA”。
  - 改正文时只改了 PR 正文，仓库内的同一句话没有同步（与 S16 议题 2 是同一类问题的另一面）。
- **改进**：
  - 行动 2：发布送审清单加三条自查，附输出：
    - (a) 发布文档与 PR 正文中的 git 范围不含 `main` / `HEAD`：`rg -n '\.\.(main|HEAD)\b' CHANGELOG.md docs/release docs/demo/<版本>` 应无输出；
    - (b) 每条“没有 / 未测 / 不适用”的说法都链接到来源 PR 中的检索结果；
    - (c) 控制字符检查：`rg -n '\t' CHANGELOG.md docs/release` 应无输出。
  - 改 PR 正文的同时，用同一个检索在仓库内的文档里查找同一句话。

## 议题 3：构建来源被打回（stash 调整过的工作区）

- **发生了什么**（观察）：#278 第 1 轮（[6029540342](https://github.com/lingshf/ai-native-erp/pull/278#pullrequestreview-6029540342)）：base 构建是在开发 worktree 里 stash 之后得到的，不是精确合并基 `26b16b0` 的干净检出；也缺完整 SHA、lock blob 与产物摘要。补上干净的分离检出后，结果不变（6285 → 6282 B）。S17 另一处证据问题是 #275 R4 只发布了摘要前缀（待证据）。
- **根因**：
  - 任务书模板“构建来源”要求“干净工作区”，但没有定义什么算干净。stash 之后 `git status` 为空，按字面也算干净。
  - S15 行动 1（数字出现即附证据）已写入路线图 §5，但“附证据”没有规定证据的最低形式，所以摘要可以截断，base 可以是调整过的。
- **改进**：
  - 行动 3：任务书模板“构建来源”把“干净”写成可检查的形式：
    - base 与 head 各用一个新建的分离 worktree（`git worktree add --detach <dir> <完整 SHA>`）跑 `npm ci` 与相同的构建命令；
    - 块中附 `git -C <dir> rev-parse HEAD` 与 `git -C <dir> status --porcelain` 的输出（应为空）；
    - 摘要一律写完整 SHA-256，不截断；
    - 在开发 worktree 里 stash、reset 或 checkout 得到的构建，不算构建来源。

## 议题 4：任务书的断言在修复后的 head 上不成立（D485，设计侧）

- **发生了什么**（观察）：FIX-TADJ-BUSY 任务书 F2 第 5 步要求过期结果落定后立即断言“账套选择可用”。账套选择的禁用条件是 `guard.busy || guard.unsaved`，此时草稿还在，所以修复后它照样禁用。开发在 head 上实测发现了这一点，把断言移到“清除草稿”之后（D485），评审认可。
- **根因**：我的设计试跑只在 base 上确认用例失败，并记录了“账套选择禁用 = true”；在试改后的 head 上只跑了整体通过与否，没有逐条跑任务书写下的断言。路线图 §5 设计自查第 11 条要求“证明条款先做可行性核对”，但没有要求在试改后逐条核对断言。
- **改进**：
  - 行动 4：缺陷修复类任务书的设计试跑，必须把任务书中写下的每一条断言分别在 base 与试改后的 head 上各跑一次，并按条记录“base 失败 / head 通过”；只能在一侧成立的断言要写明理由。写入路线图 §5 设计自查第 11 条与任务书模板设计自查。
