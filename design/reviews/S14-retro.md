## 议题 1：构建来源在三个开发 PR 里都是待证据

- **发生了什么**（观察）：#238、#240、#242 各有 1 轮待证据，内容相同，都是字节比对的“来源”没有附全：
  - #238：R4 字节表没写实际构建两份产物的完整 base / head SHA 与 Node 版本；
  - #240：Q4a / b、Q4c 的比对脚本原文没有附或链接；
  - #242：构建说明只写短 base 和未指明的 head，缺 Node 版本，评审要求补“构建来源”块。
- **根因**：
  - S14 任务书写了“构建条件同 S13 REFAC-03 M4”，没有列出“构建来源”具体包括哪几项（完整 SHA、Node / npm、lockfile、干净工作区、产物摘要）。三个开发各按自己的理解写，评审按“可独立复现”判。
  - S13 回顾行动 6（证明类验收附脚本原文与未截断输出）在 S14 期间还没写入路线图（随 #247 才写入），S14 的开发 PR 不受它约束。
- **改进**：
  - 已做：S15 共同验收加了“构建来源”条款（#247，按 #242 的格式），REFAC-06b B4、REFAC-06c P7 明确要求。
  - 行动 1：把“构建来源”块写进任务书模板的“证据要求”，凡有字节、耗时等构建产物比对的任务自动继承，不再靠每个 Sprint 的共同验收重写。

## 议题 2：发布说明里的数字没写清测量对象

- **发生了什么**（观察）：#243 打回 2 轮，都在同一句话上：
  - 第 1 轮：发布说明把 REFAC-06 的 +3 B 写成“发票页 +3 B”。+3 B 是首屏入口的屏蔽哈希 gzip-9 差（D454 视同 ±0），发票相关路由实际是各 −23 B。
  - 第 2 轮：改写后的“被 gzip-9 掩盖”仍不准确：gzip-9 没有掩盖任何东西，差异来自预加载顺序。
- **根因**：
  - 发布说明从 PR 正文转写数字时，丢了“哪个产物（入口 / 某路由）、哪种口径（原始 / 屏蔽哈希 gzip-9）”这两个限定。S12 行动 4 只要求视觉数值写明测量对象，没有覆盖体积数字。
  - （推断）S14 的体积数字有三种方向（四路由大幅下降、入口小幅上升但视同 ±0、发票路由小幅下降），简写成一句话时最容易混。
- **改进**：行动 2（版本管理）：发布说明与 CHANGELOG 中每个体积或耗时数字都写明“产物 + 口径 + 来源 PR”，例如“入口，屏蔽哈希 gzip-9，#242”；送审清单加一项：逐个数字对照 PR 正文的原表。

## 议题 3：预加载顺序的例外裁了三次

- **发生了什么**（观察）：
  - REFAC-05 首屏 +1 B → D452（±2 B）；
  - REFAC-04 入口 +13 B，其中 4 B 来自预加载顺序 → D453 补记；
  - REFAC-06 实测 +6 B，超出 D452 → D454 改为“排序后文本相同 + ±10 B”。
  - 三次差异性质相同：Rolldown 按模块访问顺序排列 chunk imports，拆分模块就会改变顺序。
- **根因**：S12 行动 5 要求预算先在实际 base 上试算，但 S14 计划只对“新增字节”试算，没有预见“只改顺序也会改 gzip 字节”。首屏 ±0 是严格相等，任何拆分都可能碰到。
- **改进**：
  - 已做：S15 的 REFAC-06b B4、REFAC-06c P7 都明确“首屏按 D454”。
  - 行动 3：把 D454 的四条判定写进路线图 §5 或任务书模板，作为所有拆分任务首屏比对的默认方法，不再按 Sprint 逐次裁定。

## 议题 4：Demo 时段前没有做演练

- **发生了什么**（观察）：DEMO-14 时段前没有做 `slot-run -Stub` 桩演练，也没有做不带浏览器的演练；README 自述“两者都需要启动 node，按 D442 没有申请”。#245 评审指出 D442 只约束时段内其他会话，不豁免模板第 12 条。D457 接受偏差，不重拍。同时同一语言的 7 页复用一个浏览器上下文，`capture.mjs` 文件头在运行后改过。
- **根因**：
  - 演练要在申请时段**之前**做，但申请时段、协调者宣布时段、D442 停用 node 几乎是同一时刻。版本管理把 D442 理解为“时段相关的一切都不能起 node”，演练就没有可做的窗口了。
  - 模板第 12 条只写了“申请前先演练”，没有规定时段申请要附演练记录，协调者批准时段时也没有检查。
  - S13 回顾行动 5（Demo 脚本时段外先跑通）的落点在 DEMO-15，S14 期间尚未生效。
- **改进**：行动 4（版本管理、协调者）：时段申请消息附桩演练与无浏览器演练的记录链接（命令、退出码、时间）；协调者没看到记录不批准时段。上下文要求按 D457 执行（每页独立，或在记录里论证复用无影响）。

## 议题 5：设计文档的计数和措辞不准

- **发生了什么**（观察）：设计打回 4 次，比 S13 的 8 次少一半，性质也变了：不是条款在 base 上执行不了，而是文档自身不准：
  - #234：Q4c 的判定前后矛盾；样式导入的许可范围在四处写法不一致；
  - #237 第 1 轮：时段统计漏记 2 次；D451 已认可仍写“待定”；D439 的原预算写错；
  - #237 第 2 轮：README 索引仍写“待协调者认可”；
  - #244：零采样的描述说过头了。
- **根因**：
  - 评审与回顾的计数靠人工从 PR、日志和 README 里拼，没有一份可重放的原始列表；同一事实在正文、表格、索引里写了几遍，改了一处漏了另一处。
  - （推断）“全部 / 一直 / 都是”这类全称说法没有逐条对照原始记录。
- **改进**：行动 5（设计）：Sprint 评审的打回、待证据、时段与 Full 计数，用 `gh api` / `gh run list` 生成原始列表，命令写进评审文档；同一事实只在一处写全文，其他位置链接过去；全称说法逐条附出处，否则改为具体数字。

## 议题 6：拆分后文档里的 file:line 引用过时
